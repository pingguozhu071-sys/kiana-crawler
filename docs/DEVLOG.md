**两个方法论教训（都记在这儿免得重犯）**：

1. **我自己写错过一个假变异**：把 `save_secret_json` 换成 `save_protected` 当成"不加密"——

## 2026-10-01 · v2.19.8 —— **第一次真机跑通**：一次实测抓到 2 个真 bug + 1 条假通过测试

机主给了 8 个 B 站短链 + 2 篇公众号 + 自己的 bilibili cookies，说"你自己判断自己动手弄"。
我按**无界面模式**跑（不需要机主在场，日志自己读）——这是本项目**第一次真的在公网上跑**。

### 一、实测结果

```
命令：run_crawler.py https://b23.tv/n2vFgzi -m 3 --no-video --no-image --cookie-file <机主cookies>
结果：106 秒，12 页成功 / **fail=19**，产出 13 JSON + jsonl/csv/markdown + **126MB mp4**
```

### 二、**bug 1（已修 + 真机复验）**：`--no-video` 被"种子捷径"绕过

明传 `--no-video`，仍产出 126MB 的 mp4。

`crawler.py` 的 `is_video_platform` 种子分支**只判断"是不是视频平台页"，从不检查 `self._dl_video`**
—— 普通页面路径有守卫，这条**种子捷径没有**。

修法：包一层 `if self._dl_video:`，关闭时记可读日志（"仅入页面解析队列"），
**页面解析通道不受影响**（封面/标题/相关链接照收）。

**真机复验**：同一命令 → **26 秒、9 页、产出里没有任何 mp4**。
（顺带快了 4 倍——126MB 的下载本来就是白花的。）

### 三、**bug 2（已确诊 + 已派修）**：短链没被还原 → **19 个失败的唯一原因**

证据（内部日志）：
```
discarding data: https://b23.tv/video/BV1PSL96YEwp?amp%3Btrackid=...
page_processor: JS 渲染站点: https://b23.tv/video/BV1PSL96YEwp?amp%3Btrack
```

真实页面在 `www.bilibili.com/video/BV1zJhr6bEVa`，相关推荐是**相对链接** `/video/BVxxx`，
但解析基址用的是**原始种子** `https://b23.tv/n2vFgzi` → 拼成 `https://b23.tv/video/BVxxx`
（该网址不存在）→ 19 个全灭。

**根因**：`url_utils.safe_get()` 为做 SSRF 逐跳校验刻意 `allow_redirects=False`，
自己用 `urljoin(_cur, _loc)` 跟跳转 —— 循环里**维护着 `_cur`（终址）却没往外带**，
于是下游 `parser.py` 的 `urljoin(url, ...)` 仍以**请求前的 url** 为基址。

**影响面不止 B 站**：任何短链种子（t.cn / 微博 / 抖音…）都会这样。

### 四、**bug 3（已修）**：又一条 flaky 门禁用例

`test_m3_solver_service.py::TestServiceSideGate::test_unknown_path_is_404`
—— **单独跑 15/15 全过，全量跑偶发失败**。

该文件原先一律 `timeout=5` 打本地回环。这些用例**验的是 HTTP 状态码（400/404/504），不是延迟**，
5 秒把"机器忙不忙"扯进了判据（前序测试留下的后台线程会在负载下抢 GIL）。
改 30 秒：**判据不变，只是不再顺带考核机器负载**。

> 这是本会话**第二条** flaky 门禁用例（第一条是 CSV BOM 的秒边界）。
> **两条都在发版门禁里** —— 门禁会随机变红，比"没有门禁"更消耗信任。

**把"已评估、决定不改"和"从没看过"混在一张表里**，是最危险的一种台账——

原实现：`any(m in host for m in markers)`，**按字典顺序取第一个命中**。

fake-jd.com          →  'jd'       ❌
taobao.com.evil.com  →  'taobao'   ❌   ← 经典的域名后缀伪造

### 三、修法：域名边界匹配 + 最长标记优先

```python
if (host == m or host.endswith("." + m)) and len(m) > best_len:
```

- **域名边界**：`nottaobao.com` 不以 `.taobao.com` 结尾 → 不再误判；
- **最长优先**：`2.taobao.com`(11) 胜过 `taobao.com`(10) → 闲鱼归闲鱼；
  且**不再依赖字典顺序**——将来加 `item.jd.com` 这类更具体的标记也不会被覆盖。

## 2026-09-30 · v2.19.8 —— 域名提取：**三份实现、两种不一致**，其中一种真实可达

### 一、怎么找到的（第 14 项工具上线后的第一次实战）

门禁第 14 项把 39 个"同名同签名"的分叉列了出来。用**实现体相似度**分档后，
`_domain_of` 出现在 `rate_limiter` 与 `session_pool`（相似度 0.805）——
而 `url_utils` 里还有第三个 `extract_domain`。把三者放到同一组输入上跑：

| 输入 | `extract_domain`（旧） | `rate_limiter._domain_of` | `session_pool._domain_of` |
|---|---|---|---|
| `example.com`（裸域名） | **`''`（空串）** | `example.com` | `example.com` |
| `https://[`（畸形） | **抛 ValueError** | `unknown` | **抛 ValueError** |
| `not a url` | `''` | `not a url` | `not a url` |

### 二、为什么这是真缺陷（不是"实现风格不同"）

`extract_domain` 的调用点**全仓只有两处**：`frontier.push` 与 `redis_frontier.push`
——**都是写 `domain` 列**。于是：

- **裸域名种子**（用户直接粘 `example.com`）会让 `frontier.domain` 存成**空串**：
  所有裸域名种子挤进同一个空桶，而限流器与会话池却按 `example.com` 分桶
  → **域名限额、域名级冷却、`count_done_by_domain` 全部错位**；
- **畸形 URL 会抛异常**，而该函数在 `frontier.push` 里被调用、`push` 在**爬取主循环**上。

### 三、修法：收口到唯一实现

`extract_domain` 改为**像主机名就补 scheme**（仅限 `_HOSTLIKE`，垃圾输入行为不变）、
**绝不抛异常**（失败返回 `""`）；`rate_limiter._domain_of` 与 `session_pool._domain_of`
**改为委托**。三处实测**0 条不一致**。

顺带清掉两处因收口而失效的 `from urllib.parse import urlparse`（我引入的未用导入）。

### 四、同时把静态基线**收紧**

清理后 ruff 实测 **81**，而门禁上限写的是 **84** —— 那 3 点余量就是**新的隐性容忍**：
"再加 3 个静态错误门禁也不会响"，与当年被余量放过的 P2-13（F821 未定义名）是同一个洞。
已按实测值锁死为 **81/103**（原 84/104）。

### 五、验证

新增 `tests/test_domain_extraction_single_source.py`（6 例）：三处实现在全部用例上
**必须一致**（含那三个曾分道扬镳的输入）；裸域名不得为空；**绝不抛异常**；

## 2026-09-30 · v2.19.8 —— 门禁第 14 项：把"找下一个分叉"从**人肉**变成**工具**

### 一、为什么要工具化

连续九轮验证下来，本工程最稳定的缺陷模式是**同一个能力在多处各写一份**：

| 轮 | 能力 | 发现 |
|---|---|---|
| 18 | WebRTC 泄漏面 | 5 份实现，2 份**各漏一条路径** |
| 19 | 下载会话 impersonate | 3 份拷贝，**只修了 2 份** |
| 23 | UA↔TLS | 主通道修过同源绑定，**下载链没跟** |
| 24 | 重试策略 | Redis 后端是**陈旧分叉**，落后 3 次修复 |
| 25 | 后端接口 | `push`/`pop_batch` 形参不符 → **TypeError** |
| 26 | 防盗链 Referer | **三种做法**，两种正好命中 403 形态 |

而此前每轮都是我**人肉去找**"下一个能力是什么"——**这本身就是不可靠的做法**，
更不能指望后来者接着人肉。故做成门禁第 14 项。

### 二、判据是**实测校准**出来的，不是拍脑袋

工具扫"同名函数/方法跨 ≥2 个模块"，分三档：

| 档 | 判据 | 处理 |
|---|---|---|
| `signature_mismatch` | 2 个模块 + 形参不一致 + 无 `**kwargs` | **阻断**（调用点可能 TypeError） |
| `generic_name` | 出现在 **≥3 个模块** | 只登记 |
| `same_signature` | 其余（含 `**kwargs` 纯委托） | 只登记 |

**为什么这样定档**：先按"形参不一致就报"跑了一遍，得到 17 个，逐条人工核对后发现——
真出事的（`push`/`pop_batch`/`mark_failed`/`normalize_url`/`sanitize_video_filename`/**全是 2 个模块**），
而 `acquire`/`record`/`release`/`solve`/`save` 这些 **≥3 个模块**的全是**无关类共享的通用动词**
（信号量 / 限流令牌 / 浏览器槽位 / 指标记录）。

`**kwargs` 必须视为兼容：`f(*args, **kwargs)` 能接住任意关键字实参，
不处理这点会把 `write_page` / `write_error` 这类**正常委托**误报成失配——
**第 25 轮我自己就踩过这个坑**。

### 三、工具上线就抓出两处**孤儿重复实现**

| 重复 | 情况 |
|---|---|
| `DataCleaner.normalize_url`（`adaptive_v2.py`） | **第二个 URL 规范化实现**，与 `url_utils.normalize_url`（引擎用于 `url_hash` 去重的那个）**语义不一致**：本地版缺 IDNA 规范化、缺默认端口剥离、缺 `..`/`.` 路径段解析、缺 tracking 参数过滤——**同一个 URL 两边得到不同字符串**。若哪天拿它当去重键，就是"同一页爬两次"或"两页被并成一个" |
| `page_processor.sanitize_video_filename` | 与 `m3u8_downloader` 的同名函数**语义不同**（前者取 URL 后 60 字符、允许 `.`；后者剥 Windows 非法字符、取前 200），且**生产路径上从未被调用**（`crawler` import 的是 `m3u8_downloader` 那个） |

两者**都是死代码**（生产路径零调用，`DataCleaner` 只用到 `filter_junk_url`），
但**看起来都像权威实现**——后来者很容易 import 错那个弱的。处置：

- `DataCleaner.normalize_url` → **改为委托唯一实现**（形参也对齐，扫描器不再报它）；
- `page_processor.sanitize_video_filename` → **删除**（已确认全仓无 import、无调用）。

处置后形参不一致从 **17 → 6**，剩下 6 个（`_tune`/`_walk`/`fetch`/`invalidate`/`process`/`save`）
逐条核对确认为无关类共享动词，登记入基线。

### 四、验证

新增 `tests/test_duplicate_capability_scan.py`（12 例）：三档判据各自的边界、
`**kwargs` 兼容（含"首版夹具写错、那是夹具错不是代码错"的记录）、

## 2026-09-30 · v2.19.8 —— 重试策略：Redis 后端是一个**陈旧分叉**，漏掉三次修复

### 一、问题（两个后端，一份策略，各写各的）

`mark_failed` 在 `frontier.py`（SQLite）与 `redis_frontier.py`（Redis）里**各写了一份**。
SQLite 那份身上叠着历次修复的长注释，Redis 那份**一条都没有**：

| | SQLite | Redis（修复前） |
|---|---|---|
| 退避 | `delay × 1.8^n × U(0.7,1.3)`，封顶 600s | **固定 `delay`** |
| 限流 | `throttled` → 不消耗 `retry_count`，另计上限 10 | **忽略 `throttled`** |
| done 守卫 | 三条 UPDATE 带 `AND status != 'done'` | **无** |

于是三件**已经在 SQLite 上修好的事**，在 Redis 后端全部还在：

1. **重试风暴**（v2.14 修复）——Redis 仍是固定 delay，
   等于退回"同域 50 任务 30s 后**同步**重新出队形成周期性打波"的版本；
2. **"3 次限流即 dead"**（v2.17 E-P1-3 修复）——Redis 把限流当普通失败消耗 `retry_count`；

把策略抽成 **纯函数** `frontier.next_retry_state(...)`（**不做任何 I/O**），

- `frontier.mark_failed` 改为调它（SQL 语句与守卫**逐条保持原样**）；
- `redis_frontier.mark_failed` 改为调它，并补上 **done 守卫**；
- 降级到 SQLite 的路径也把 `throttled` **带下去**——否则语义会在降级时丢失
  （原实现的降级调用就没带）。

求解引擎抛异常（浏览器崩 / CDP 失联 / 超时）会被**无声吞掉**，调用方只看到 `None`。
于是"**求解器崩了**"与"**求解器没给出可用响应**"变得**无法区分**。

**为什么这一处特别要紧**：整条回退链存在的意义就是回答"**这个站为什么失败**"——
M2 的结构探针、trace 取证、CDP 探针全是为这个问题服务的。
而这里是回退链上**最该留下线索**的一处：它恰好是异常发生的地方。

### 二、修法

计数 + 记日志，**不改变控制流**（回退链必须继续走）：

```python
except Exception as e:
    self.solver_exceptions += 1
    logger.warning(f"[{self.FALLBACK_SOLVER}] 求解异常，按无响应继续回退 "
                   f"(已计 {self.solver_exceptions} 次): "
                   f"{type(e).__name__}: {str(e)[:120]} | {url[:60]}")
```

- `self.solver_exceptions` 在 `__init__` 里初始化为 0（**可观测性**，不是内部状态）；
- 日志走根 logger 过滤器 → URL 与内容自动脱敏（第 13 项保证的那条链）；
- `finally` 归还代理的既有行为**不动**（异常路径也不能漏掉出口）。

### 三、门禁第 12 项的闭环用法

修完后**跑一遍扫描**：热路径静默失败 70 → **69**，然后 `--write-baseline` 更新。
门禁当场给出进步：

```

```

这就是第 12 项想要的工作流：**修一处 → 基线变小一处**。
存量 70 处不搞一次性大扫除，但每修一处都有账。

## 2026-09-30 · v2.19.8 —— 门禁第 12 项：热路径静默失败扫描（让一条**无法核对**的纪律可核对）

## 2026-09-30 · v2.19.8 —— M3-b（框架）：求解进程隔离 —— 服务侧与引擎侧**双重过闸**

**动机**：`solver_engine` 现在是**进程内池**。浏览器崩一次会拖累引擎——工程用
"渲染预算"在防，但那是**防量**，不是**防崩**。本步给出"崩了重启服务、不重启引擎"
的形态与契约。

### 一、三条必须守住的（方案点名，破一条这功能就是负资产）

**① 服务侧与引擎侧都要过 SSRF 闸。**
只信一侧等于把闸挪了个位置；两处**独立判定**才是纵深防御。
本模块把闸抽成 `gate(url)` 一个函数，两边各自调用。
有专门的用例**绕过客户端**直接打服务，确认服务侧自己也拦。

**② 拦截态必须是 400。**
403 在本工程是"**请升级到浏览器**"的信号，而求解服务**恰恰就是浏览器层**——
回 403 会让上层把"被闸拦下"误读成"该换浏览器通道"，于是拿**同一个私网 URL**
再走一遍没有闸的路径。**这正是 v2.19.6 那次事故的形状**，所以这条单独立了用例。

| 状态码 | 含义 | 可重试 |
|---|---|---|
| 400 | 被闸拦下 | ❌ **不可重试** |
| 504 | 求解超时 | ✅ |
| 503 | 服务不可用/浏览器崩 | ✅ |

**③ 服务不可用按既有失败语义降级。** 客户端**不抛异常**，所有失败都转成带
`retryable` 的 `SolveOutcome`，**绝不静默假装成功**。

### 二、形态

- 服务**只绑定 `127.0.0.1`**（不对外暴露），`ThreadingHTTPServer` + 一个
  `POST /solve` 端点；
- 引擎侧客户端在**引擎进程内**，`solve()` 经 `asyncio.to_thread`（不冻事件循环）；
- **不改退出码契约**：客户端不参与 `sys.exit`，0/1/2/3 仍由原链路决定。

### 三、验证

新增 `tests/test_m3_solver_service.py`（11 例）。**用本机回环 HTTP 服务做端到端，
不启动任何浏览器**（零显存）：

| 组 | 锁什么 |
|---|---|
| 绑定 | 服务只监听 `127.0.0.1` |
| 引擎侧闸 | 私网 URL 在**服务都连不上的端口**上也返回 blocked（证明确实在发请求**之前**拦的）；非 http/https 同样拦 |
| **服务侧闸** | **绕过客户端**直接打服务 → 返回**字面量 400**、断言≠403、且**被拦的 URL 压根没触达求解器** |
| 端到端 | 成功往返；求解超时→504可重试；求解抛异常→503可重试 |
| **中途被杀** | 服务 `shutdown` 后再请求 → 可重试失败，**不崩也不假装成功** |

**反证（变异注入）**：

| 变异 | 结果 |
|---|---|
| `ST_BLOCKED` 改成 403（那个语义坑） | ✅ `test_private_url_gets_400_not_403` FAILED |
| 移除**服务侧**闸（只留引擎侧） | ✅ 同一条用例 FAILED（私网 URL 直接触达求解器） |

**测试自身也修了一处**：初版断言写的是 `code == ss.ST_BLOCKED`——
用**定义它的常量**去断言它，等于"常量改成 403 测试还绿"。已改为断言**字面量 400**
（状态码是对外契约，不许随常量漂移）。这与前几轮 `ast.unparse` 那次是同一类教训。

**全量**：`823 passed, 1 skipped`（基线 677+1，累计 +146 例，**0 失败**）。

### 四、顺带补齐一个"隐形默认值"

`browser_render_max` **此前只存在于读取端的兜底里**
（`page_processor` 写 `cfg.get("browser_render_max", 20)`），`DEFAULT_GLOBAL` 里**没有**
——于是它既不出现在配置模板、也不受"唯一默认源"约束，等于一个**隐形默认值**。
已在 `DEFAULT_GLOBAL` 补上（读取端兜底保留，两者同值）。

### 五、如实标注：本步只做了**框架与契约**，未接线

`SolverEngine` 仍是进程内池；把回退链切到本服务、以及并发/冷却/渲染预算的重新校准，

## 2026-09-30 · v2.19.8 —— M2-d：trace 取证（脱敏归档，从零做）

**背景**：白皮书 §8 写着"有几个线上解析器失败原因尚未定位"。补证据的工具其实**就在
既有依赖里**——patchright/playwright 自带 trace 录制（DOM + 网络 + 控制台）。
本工程此前**零 trace 机制**（已 grep 确认），本步从零做。

### 一、为什么"直接归档"是危险的

trace 里有三样东西比日志更敏感：

- **完整请求 URL**（含签名参数 `?token=…`）；
- **请求/响应头**（含 `Cookie` / `Authorization`）；
- **页面 DOM**（登录后才可见的内容）。

而且它比日志**更危险**：日志有脱敏 Filter 兜着，trace 是**原始结构**，筛选器够不着。

### 二、三条红线（写进代码注释，防后人"顺手清掉脱敏"）

1. **归档前必须过脱敏**——有对抗性回归（下节）。
   脱敏失效比不归档更糟：它给出"已经处理过了"的错觉。
2. **归档目录不参与任何导出**——与 `frontier` / `video_downloads` 同原则：
   敏感 URL 收口在导出侧，而这份**根本不出现在交付物里**。
3. **归档落运行期数据根，不进仓库**——反面教材就在本工程：
   `tests/assets/gui_shots/` 是**被 git 跟踪的**，测试截图一旦落进仓库就会被打包、
   提交、公开（历史上正是像素级泄漏的来源）。取证归档更不能重蹈。
   便携模式（`KIANA_PORTABLE=1`）下数据根会落成 `<仓库>/KianaData/`——该目录已在
   `.gitignore` 里，且有断言把这个前提**钉住**。

### 三、脱敏怎么做的

- **逐行处理**：能解析成 JSON 的行做**结构脱敏**（可靠，能处理 Playwright 的
  `[{"name":"cookie","value":"…"}]` 数组形态与 `{"cookie": "…"}` 字典形态）；
- 解析不了的行走**保守正则兜底**——**宁可多抹，不可漏抹**；
- URL 一律过既有的 `sanitizer.sanitize_url`（复用，不另造一套）；
- **二进制资源原样复制**（截图等），条目集合不变——但整个目录不参与导出；
- **原始 trace 只读**：脱敏产物另存，便于对照，也避免"改坏了原件"。

## 2026-09-30 · v2.19.8 —— M2-a：结构指纹与变化告警（线上探针的地基）

**背景**：工程有 752 条离线用例，它们证明的是"规则**没坏**"，**证明不了"站点还能用"**。
白皮书 §8 自己就写着"部分解析器只有离线证据""有几个线上解析器失败原因尚未定位"。
M2 补的就是这个差额——给每个解析目标算一个**结构指纹**，结构一变即可告警。

### 一、为什么不是"全文哈希"

全文哈希（或对整页做 simhash）会把**内容变化**也算进去：换个日期、换条推荐、改个
价格就报警，噪声大到没人会看。所以指纹只反映**结构**：

- 每个元素贡献 token：`<tag>`，有 class 时再加 `<tag>.<首个类名>`；
- `script/style/noscript/template/svg` 跳过（随改版频繁变，且与页面结构无关）；
- 超大页截断 3000 个 token，避免单页把指纹计算拖死；
- 复用工程既有的 `parser.simhash_64` 与 `simhash_hamming`。

**文本内容完全不进 token** → 文案/日期变了指纹不动，结构变了才动。有专门回归锁死。

### 二、探针失败 ≠ 结构变化（本模块最容易写错的一条）

`decide()` **探针失败优先**：任一侧指纹为 0（页面取不到 / 解析不了 / 被拦）时返回
`PROBE_FAILED`，且**连续次数原样返回**——不累计、不惩罚。理由与 M1-e 的
"探针超时不判死"同源：**站点临时抽风不能把规则判死**；若算作一次"结构变了"，
抽风三次就会误报"站点改版"，探针立刻变成噪声源。

判定三档：`ok`（达标，且**连续计数清零**）/ `warn`（单次低于阈值，**只告警**）/
`changed`（**连续 3 次**低于阈值才判结构变了）。

### 三、观测数据不进版本库

`FingerprintStore` 默认落 `data_root()/probe/fingerprints.json`（运行期数据根），
**不在仓库内**；写入走"临时文件 + 原子替换"，避免半截文件被当成有效指纹；
读/写失败都**告警而非静默**（读失败静默会让"指纹全丢"被误当成"全是新站点"）。

### 四、验证

新增 `tests/test_m2_fingerprint_probe.py`（13 例）：

| 组 | 锁什么 |
|---|---|
| token 抽取 | 只出结构、**不出文本**；script/style 跳过；空/垃圾输入返回空 |
| 指纹 | **文本变→指纹不变**（区别于全文哈希的核心）；结构变→指纹变且相似度跌破阈值；空页→0 |
| 判定 | 相似→ok 且计数清零；1/2 次→warn、第 3 次→changed；**探针失败不累计**；**连续 10 次失败也绝不判 changed** |
| 存储 | 首次运行无库→空；往返一致；无残留 `.tmp`；写失败返回 False；**默认路径不在仓库内** |

故改为注入两个**针对性变异**：

| 变异 | 目标用例 | 实际 |
|---|---|---|
| 指纹里掺入页面文本 | 文本变→指纹不变 | ✅ FAILED |

两个变异共触发 **3 failed / 10 passed**（多出那条是"连续失败也不判 changed"的连带
断言，说明该纪律有纵深防护）。恢复 → 13 passed。

## 2026-09-30 · v2.19.8 —— M1-c（完成）：按站身份回路真正接进引擎

**背景**：M1 的核心承诺是"登录态可用"。M1-b 造好了原语、M1-c 第一步拆了消音器，
本步把**回路接通**：每页抓取前取一个按站账号、抓完按结果反馈。

### 一、接线设计（为什么是"页面级租约"而不是"每请求查库"）

`ProtocolEngine._build_headers` 是**同步、每请求**调用；而弹药库的 acquire/report 是
**每次任务/每页**的语义（带额度与冷却）。若在 `_build_headers` 里查库，等于每个 HTTP
请求开一次写事务，且拿不到响应状态、无法反馈。

故采用**页面级身份租约**：

```
page_processor._fetch_with_identity(url, domain, job)
  ① acquire_identity(domain)         ← 经 asyncio.to_thread（不冻事件循环）
  ② protocol.install_cookie_lease()  ← 注入点仍是 _build_headers（唯一）
  ③ router.fetch(...)                ← 抓取
  ④ report(domain, name, result)     ← 按状态码反馈
  ⑤ finally: clear_cookie_lease()    ← **绝不跨页残留**（残留 = 用错账号）
```

**优先级**：用户自填 cookie（`extra_headers`）> 页面租约 > 打包池（`identity_bundle`）。
既有语义全部不变；租约为空时（未启用）行为与引入前**完全一致**。

### 二、状态码 → 反馈语义

| 状态码 | 反馈 | 理由 |
|---|---|---|
| 403 / 429 / 503 | `THROTTLED` | 限流/风控 → 扣分 + 冷却 |
| 401 | `LOGIN_EXPIRED` | 明确要登录 |
| 其余（含 404） | `OK` | 抓取本身成功；页面不存在 ≠ 身份坏了 |
| 抓取抛异常 | `NETWORK` | **不惩罚身份**——网络抖动 ≠ 身份坏了（防误杀，同 M1-e） |

### 三、诚实降级与"零影响"

- **未配置弹药库** → `cookie_armory` 为 `None` → 直接走原 `router.fetch`，**零变化**。
- **身份不可用**（未提供/全冷却/额度用尽）→ 记一条**可读**日志（含原因与详情）后
  按无 cookie 抓取。**绝不**静默假装有身份——那会让登录墙表现成"页面内容不对"。
- **启用失败**（取不到主密码等）→ 明确降级为"本次不启用"并告警，**不静默、也不假装启用**。
- 新配置键 `cookie_armory_enabled` 进 `DEFAULT_GLOBAL`，**默认 False**（唯一默认源）。

## 2026-09-30 · v2.19.8 —— M1-e：探针三态（超时不判死）+ 补上不存在的错误聚合

`check_bilibili` 原实现：

## 2026-09-30 · v2.19.8 —— M1-b：身份层 acquire/report 原语（含一个"永久拉黑"真缺陷）

**背景**：M1-a 把 `accounts` 的容器备好了，M1-b 往里放身份层的"取 / 反馈"原语。
动手前回源核实，发现 `CookieArmory` 里有两个**会把问题吃掉**的真缺陷。

### 一、真缺陷：身份会被**永久拉黑**（本轮最要紧的一条）

`acquire` 的条件是 `health_score > 0.0`，而 `report_failure` 把分数钳到
`max(0.0, ...)`——扣分步长 0.25，所以**连败 4 次**（1.0 − 4×0.25 = 0.0）之后：

- 该身份**永远**不满足 `> 0.0` → 永远选不中；
- 也就永远等不到 `report_success` 的 +0.1 回血 → **永久拉黑，且没有任何告警**。

冷板凳的语义应当是"暂时靠后"，不是"永久删除"。修法（**不动扣分与冷却语义**）：
冷却到期时把它**复活到下限** `_REVIVE_SCORE = 0.1`。惩罚效果原样保留
（分数最低 → 排在选择序列最后），死锁消除。

> 没有改钳位数值，也没有改冷却时长——只加了一条"到期复活"路径，
> 因此既有惩罚行为与全部旧用例都不受影响。

### 二、两处 `except Exception: pass`：记账失效无声无息

`report_success` / `report_failure` 的落库失败此前被完全吞掉：**健康分与冷却记不上，
而调用方以为记上了**。现改为：失败打 ERROR 日志（含堆栈）并**返回 False**。
返回值是新增的——旧调用方忽略它也不受影响。

### 三、新增统一原语（旧 API 保留为薄包装）

- `acquire_identity(site, *, purpose)` → `Acquired` | `Unavailable`，**不抛异常**；
- `report(site, name, result)`，`result ∈ {OK, THROTTLED, LOGIN_EXPIRED, BLOCKED, NETWORK}`；
- `Unavailable` 带**可读原因**：`NOT_PROVIDED` / `ALL_COOLING` / `QUOTA_EXHAUSTED` /
  `DECRYPT_FAILED` / `DB_ERROR`——调用方能区分"没有身份"（走诚实降级）与"库坏了"。

**原子性**：选择与额度记账在同一个 `BEGIN IMMEDIATE` 写事务内完成。
读→改→写跨事务边界就是真竞态，N 个协程会同时选中同一身份（超发）。
解密是慢操作，刻意放在事务**外**，不占写锁。

**NETWORK 不惩罚身份**：网络抖动不等于身份坏了。把它算成失败会白扣 0.25 分并冷却 300s
——这正是工程反复踩的"看起来有防护、实际误杀"。对照：健康探针超时也不判死（见 M1-e）。

### 四、验证

| （恢复） | 改回复活值 | **PASS** |

## 2026-09-30 · v2.19.8 —— M1-a：`accounts` schema 收敛 + 迁移 v6

**背景**：施工方案 M1（登录态与多账号）第一步是给 `accounts` 补身份层字段。开工前回源
核实发现一个**方案没写、但会直接踩到**的问题：这张表的建表语句在 `frontier.py` 与
`cookie_armory.py` **各有一份、逐字相同**。两份都写 `CREATE TABLE IF NOT EXISTS`，
所以"新库谁先打开都能建表"没问题——但**加列**时只改一处，另一个入口打开的库表结构
就落后，运行时直接 `no such column`。故 M1-a 先收敛、再加列。

### 一、建表与加列收敛到唯一源

`frontier.ensure_accounts_schema(conn)` 成为**唯一** schema 源（幂等）：

- `FrontierDB._init_db` 与 `CookieArmory._init_db` 都调它 → **打开顺序无关**；
- 它**不推进** `user_version`——版本号统一由 `_migrate` 推，避免两个入口各写一份版本语义；
- `cookie_armory.py` 中原有的重复 DDL 已删除，改为 import 该函数。

`_migrate` 追加 `if version < 6` 块，`accounts` 补 7 列：

| 列 | 用途 |
|---|---|
| `quota_window_start` / `quota_used` / `quota_limit` | 额度记账（**按"站 × 身份"**——限流是每个身份各自的） |
| `last_error_kind` / `last_error_at` | 失败原因与时间 |
| `last_ok_at` | 最近成功时间（健康检查 TTL 的判据） |
| `identity_fingerprint` | 绑定的指纹标识 |

**存量行回填刻意保守**：`quota_used=0`、`quota_limit=0`，其余 **NULL**。
`last_error_kind` 为 NULL 才表示"从未失败过"，与"失败过但原因为空"可区分——
不用非空默认值伪装成"有过记录"。

## 2026-09-18 · v2.19.8 —— CLI/GUI 键表接线缺陷 + 门禁与工具链自纠 + ⚠️ 一次实测事故

**背景**：v2.19.7 发版后，机主问"接下来需要做什么"。我把此前调研出的 17 条漂移整理成清单，

### 一、修了一个"声明与行为不符"的真缺陷：`--page-timeout 0` 关不掉看门狗

帮助文本承诺 `0=关闭`，实际**关不掉**，原因是两处键表同时缺这个键：

| 层 | 缺陷 |
|---|---|
| argparse | `default=0` 使"未指定"与"显式 0"不可区分（`if args.page_timeout > 0` 的判断因此永远为假） |
| `run_crawler.crawl()` 的 gcfg 键表 | **根本没有 `page_timeout` 这一项** → 即使 cfg 里有值也进不了 `GlobalConfig`，引擎读到的是 `DEFAULT_GLOBAL` 的 300s |
| `launcher_v8.EngineBridge` 的 engine_cfg 翻译表 | GUI 手写在 `launcher_config.json` 的同一键同样到不了引擎 |

改法：参数默认改 `None`；显式值（含 0）无条件透传；新增纯函数 `page_timeout_override(cfg)`
（**只在显式指定时**产出覆盖项，`config.DEFAULT_GLOBAL` 保持为唯一默认源）；GUI 侧同键透传。
`config.py` 里"设为 0 可恢复完全关闭"的注释此前是**假的**，已改为真实接线说明。

   改为**以退出码为准**（0 = 干净 = 0 错），非零退出才抓计数；抓不到计数才是真异常。
2. **`--skip-network` 是死参数**：docstring 声称跳过 pip-audit，`main()` 却从未把参数传进去

## 2026-09-18 · v2.19.7 —— claude-security 深度扫描后收口（含"不盲从扫描建议"的两处刻意保留）

**背景**：对 v2.19.6 全量改动跑了 claude-security 深度扫描（多路 agent 并行 + 本机 loopback
双服务 PoC）。**未照单执行**：每条先回源码求证，其中两条按"会破坏功能"驳回，改用等效但不
触碰运行态数据的方案（见末尾"刻意不做"）。

### 最重的一条：下载通道可被重定向绕过 SSRF 闸（已 PoC 复现）

扫描在本机起两个 loopback 服务复现：外部 URL 302 → `169.254.169.254`，libcurl 默认跟随
最多 30 跳 → **内网正文以 `.jpg` 正常落盘**（status=200）。v2.19.0 只给主通道做了手动逐跳，
下载通道（通用下载/m3u8/订阅源/图片/URL 探测）仍是裸 `session.get`。

| 修法 | 说明 |
|---|---|
| 新增共享原语 `url_utils.safe_get` | 入口校验 + `allow_redirects=False` **手动逐跳复检落点**；中间跳响应显式 close（流式下不关会泄漏连接）；超跳上限返回最后一跳 |
| 接入点 | `universal_downloader`（主请求/Range 重试/图片/HEAD 探测）、`m3u8_downloader`（取文本/取字节/分片）、`feed_source.collect_feed`、`enhancements.parse_sitemap` + `discover_sitemap`、`proxy_fetcher.fetch_source`、`media_downloader._download` |
| **修 method 分派 bug** | `safe_get` 首版在"会话无 `request` 方法"时一律退化成 GET → **HEAD 探测变成整文件下载**；改为按 method 选动词（`request(verb)`／`head`／`get`） |
| **保留重试语义** | 首版把传输异常吞成 `None` → 调用方的 `except → 重试` 收不到信号，一次网络抖动就被判"永久失败"。改：**异常照旧抛出**，`None` 仅表示"被闸拦下/协议非法"（不可重试） |

### 其余修复

| 项 | 修复 |
|---|---|
| CLI 脱敏结构性缺口 | `cli.py` **从不 import config**，而脱敏 Filter 的装配是 config 的模块级副作用 → 命令行跑 `status/export` 时含 `?token=` 的 URL 明文进终端。改为在 `basicConfig` **之前**显式 import |

| `api_errors.retry_whitelist` | 生产零调用。原因：唯一需要"按平台码重试"的调用点（douyin detail API）是**同步**函数，且重试判定与响应体解析交织，无法用 async 异常驱动装饰器表达 | **保留 + 标注**（定位为面向异步调用方的预留设施） |
| `douyin_resolver` 那处注释 | 原文写"与 api_errors.retry_whitelist 一致，同步版"——**误导**（两者解决不同问题） | **注释澄清**（说明这是码表驱动的业务逻辑，无可复用关系） |
| `json_util` | 是 orjson/json 的**性能适配层**，已被 `page_processor` 真实使用 | 保留（合理设施，非"接线不彻底"） |

> 判断原则：**不为消除"零调用"而强改核心调用链**。抽象设施的价值取决于是否服务未来场景；
> 若强行接线需改动无测试覆盖的 resolver 与其全部调用方，属"为指标而改"，本工程不取。

## 2026-09-13 · v2.19.5 · 质检实测发现：安装器会破坏"另一个安装"（同款事故的根因）

**背景**：机主问"现在能自己装了吗"，我决定先实测验证上一轮修的"卸载器跨实例防护"
（该防护**从未实机验证过**）。实测结果：**防护无效**，并复现了 2026-09-06 那次事故的完整链条。

### 实测暴露的链条

```
装前:  注册表 InstallDir = ...\AppData\Local\Programs\KianaVnextPlus   （正式安装）
装到副本 C:\KianaVerify2194:
       → 注册表 InstallDir 被**无条件覆盖**为 C:\KianaVerify2194
卸载副本:
       → 卸载器的"仅当 $INSTDIR == InstallDir 才删快捷方式"条件**恰好成立**
       → 删除桌面 Kiana.lnk + 开始菜单目录

结果:  正式安装的程序本体完好，但**快捷方式消失、控制面板登记消失**
```

**根因**：安装 Section 里 `WriteRegStr ... "InstallDir" "$INSTDIR"` 是**无条件写**的。
只要装到不同目录，注册表登记就被改写，"目录比对防护"随即失效——上一轮的防护
**只防住了"卸载目录未被登记"的情形**，而覆盖写入恰好制造了"已被登记"的假象。

### 修复（v2.19.5）

| 位置 | 变更 |
|---|---|
| 安装 Section | 写 InstallDir 前先读旧值：若旧值非空且**不等于**当前 `$INSTDIR`（即装到别处）→ 存入 `PrevInstallDir` 保留 |
| 卸载 Section | 二段式：① 若本安装是登记安装 → 清理共享资源；**若 `PrevInstallDir` 指向的有效目录存在 → 恢复其注册表登记 + 重建快捷方式**（而非删完不管）② 若本安装**不是**登记安装 → 不动共享资源。且**仅当本安装是登记安装时**才删除全局注册表项（原实现无条件删，会抹掉原安装的登记） |
| 常规路径 | 升级安装到**同一目录**时 `PrevInstallDir` 不写入 → 卸载行为与原来一致（彻底清理），**不受本次修复影响** |

| 路径 | 步骤 | 结果 |
|---|---|---|
| **副本路径** | 装于 A → 装副本 B → 卸载 B | 桌面快捷方式保留 / 开始菜单保留 / A 的程序本体完好 / `InstallDir` 恢复为 A / 卸载登记（DisplayName·UninstallString·**DisplayVersion**）全部恢复为 A 的值 / 副本临时标记清除 —— **8 项全过** |

## 2026-09-13 · v2.19.6 · pr-review-toolkit 审查发现：**我的安全修复本身有根本缺陷**

**背景**：机主用 pr-review-toolkit 插件对本轮改动（v2.18.2 → v2.19.5）做专项审查。
两个 agent（code-reviewer + silent-failure-hunter）并行审计，**发现 2 处由我的修复本身制造的
缺陷**——比不修更隐蔽，因为它们看起来"已经有防护了"。

### R1【致命】SSRF 闸用 403 作拦截态 → 恰好触发"升级到浏览器"，闸被完全绕过

**链条**（agent 实测复现，我方核对确认）：

```
我的闸拦截 → 返回 ResponseAdapter(403, ...)
      ↓
engine_router._needs_solver(403) → True        ← 403 是本工程"请升级到浏览器"的信号！
      ↓
_try_solver(原始 url) → Playwright page.goto()
      ↓
浏览器**原生跟随 302** → 进 169.254.169.254 → 返回 200 + 内网正文
```

`engine_router.py:160` 的 `_needs_solver` 判定 `status_code in (403, 429, 503)`；
`solver_engine.py` 全文件此前**零** `is_private_url`。

**后果**：本轮要防的"公开种子 302 到云元数据"场景**原样复现**，且**必然触发**
（拦截即 403 → 必然升级）。次生代价：每个被拦 URL 白烧 3 次已拦请求 + 占 1 次浏览器渲染预算。

**修复**：
1. 拦截态 403 → **400**（不在 `_needs_solver` 与渲染兜底的判定内，直达 `_finalize_fail`，
   且 `status>=400` 会写 errors 表 → 可诊断）
2. **浏览器层单点闸**：`solver_engine.render_simple` / `solve` 入口加 `is_private_url`，
   并在 `engine_router._try_solver` / `_try_direct` 二次把关（纵深防御，覆盖所有调用方
   含未来新增的）

### R2【高危·我引入的功能回归】重定向上限 5 + 超限静默返回 3xx → 合法链被静默判死

**链条**（agent 实测）：

```
超 5 跳 → 静默 break → 返回 302
      ↓
retryable = status>=500 or status in (429,403) → 302 **不在** → False
      ↓
mark_failed(retry=False) → status='dead'（永久，不重试）
且 if status >= 400 → 302 不成立 → errors 表**零记录**、`_finalize_fail` **零日志**
```

而 **curl_cffi 默认跟随 30 跳**——意味着 **6~30 跳的合法重定向链**
（http→https→www→CDN→区域/同意页，真实站点常见）**从"能抓"变成"静默判死、且不告诉你为什么"**。

**修复**：上限提到 **10**；超限返回 **508**、缺 Location 返回 **502**
（都是 `>=500` → 可重试 + 写 errors + warning）——不再静默。

### R3【高危】`download_video` 的闸被 fallback 绕过

`crawler` 在 `download_video` 返回 None 后走 fallback →
`media_downloader.download_direct`（**无闸**）用**同一 URL** 取了一遍。
本轮宣称的"video/audio 通道补齐一致"在 fallback 路径上不成立。

**修复**：闸**下沉到共享原语**——`media_downloader.download_direct`、
`universal_downloader.probe_url` / `stream_to_file`（一处补齐，所有调用方受益）。

### R4【中危】m3u8 闸用 `dns_check=False` → 域名型私网可穿过

实测 `http://localtest.me/seg.ts`（公开 DNS 解析到 127.0.0.1）**穿过**闸。
我原来的"性能理由"（分片数百、避免解析开销）不成立：`_HOST_CACHE` **已按 host 缓存**，
真实播放列表的不同 host 通常仅 1–3 个 → 成本是"每 distinct host 一次解析"，非"每分片一次"。
**修复**：改 `dns_check=True`；`_blocked` 的 `except` 分支加 warning（原静默放行 → 闸失效无人知晓）。

### R5【中危·新旧机制互相打脸】`mark_failed` 无状态守卫 → 看门狗把已 done 的页打回 retry

`page_timeout` **本轮由 0 改为默认 300**，看门狗 `task.cancel()` 抛 `CancelledError`
（不被 `except Exception` 捕获）→ 直接 `mark_failed(retry=True)`，
而该 UPDATE 只 `WHERE url_hash=?` **无状态守卫** → 若页面此刻**已赢 CAS**（正在持久化阶段），
`done` 被打回 `retry` → 整页重爬 + 重复导出——正是 CAS 前置想消灭的后果。
**修复**：`mark_failed` 三条 UPDATE 统一加 `AND status != 'done'`。

### R6【中危】`mark_done_checked` 把 DB 异常并入"租约易主"

原实现任何异常都 `return False`，调用方据此**丢弃已成功处理的页**，且日志写
"租约已易主，丢弃过期结果"——把排查引向完全无关的方向。
**修复**：改为**三态** `True/False/None`（赢 / 易主 / 落库失败），调用方对 `None` 抛出让外层
按失败重试（诚实反映"结果未落盘"）。

### R7【轻微】Redis 后端签名未同步

`RedisFrontier.mark_done/mark_failed` 是旧签名，本轮新增的 `leased_at=` / `throttled=`
调用点在 redis 后端下必然 `TypeError`（该页永久无法完成）。
**修复**：补齐签名（CAS 语义在无租约字段的后端**诚实降级**为无条件 done 并注明）

### R8【轻微】`logging.lastResort` 未脱敏

`lastResort` 在 `logging` 首次 import 时创建（早于我们的 patch）→ "尚未配置任何 handler"
之前的 WARNING+ 日志不受脱敏。**修复**：`_install_log_sanitizer` 里顺手挂上。

### 审查同时确认**正确**的部分（避免重复排查）

- robots 门闸的预约式占位：同步块内预定时间槽 + sleep，无 await 穿插，**无击穿**
- 渲染预算"先占位失败回滚"：数学上等价于减自己那份（计数器全仓无重置点），**未超额**
- DB 迁移 v5：新库/老库同一幂等路径；`COALESCE(throttle_count,0)` 闭环自洽
- 日志脱敏改挂 handler + 包装 `Handler.__init__`：方向正确，且验证了 `cli.py` 路径无漏网
- `curl_cffi 0.16` "Response 无 url 属性、不支持 resolve" 的判断**正确**（本轮无法事后复检的依据成立）
