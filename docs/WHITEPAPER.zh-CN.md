## 摘要

现代网页在三个层面对自动化采集布置防御：传输层的 TLS 指纹识别、执行层的 JavaScript 挑战、会话层的频度与轨迹检测；媒体类站点则把可直接下载的资源封装在带时效签名的页面内嵌数据中。本文陈述 kiana-crawler 如何在「单人、单机、无服务端」这一刻意收窄的产品边界内回答这些问题：以五级回退调度解决可达性，以租约加比较交换（CAS）协议解决并发正确性，以所有出网路径共用的一道逐跳 SSRF 闸解决出口安全，以三层脱敏及其显式写下的边界解决数据卫生，以两级令牌桶与单页看门狗解决长跑稳定性。质量由约 1,490 个离线用例与十四项发版门禁构成。文中每一项量化陈述都对应仓库内的一个出处；承载结论的数字连同可复现它的命令一并列在附录 A。

**关键词**：网页采集；反爬对抗；并发一致性；SSRF；数据脱敏；断点续传；发布工程

## 1 问题与定位

### 1.1 失效模式

单机采集有四类主导失效模式，媒体类站点再加一类。下表每一项都是设计必须承受的失败，而不是重试一次就能过去的不便。

| # | 失效模式 | 具体形态 |
|---|---|---|
| 1 | **内容取不到** | TLS 指纹识别拒绝非浏览器客户端；JS 挑战过滤不执行脚本的请求；行为检测拦截高频访问。任何单一策略都无法同时覆盖三种，而真实站点会把它们**组合**使用，因此采集端必须把多种手段按代价排序、按需升级。 |
| 2 | **并发写坏** | 同一页被处理两次、结果被互相覆盖、数据库写入交错——全部静默发生。静默是这一类最坏的性质：它不崩溃、不报错，最早的征兆是几天后产物里出现两份一样的页面。 |
| 3 | **产物不干净** | 重复内容、空壳页、他人手机号与邮箱、URL 里的会话令牌。脱敏本身也有边界，脱错位置会直接破坏功能——把队列里稍后要再请求的 URL 抹掉签名，续爬就是 403。 |
| 4 | **存活崩塌** | 一个挂死的页面拖住整批任务；设计不当的限速器把重试变成永不终止的风暴；一次网络抖动若被当成永久失败，长跑任务的完成率将永远到不了 100%。 |
| 5 | **媒体资源被封** | 播放地址藏在页面内嵌 JSON 里，带时效签名；把页面 URL 直接交给通用下载器，往往拿不到最高画质。大文件不允许「换个清晰度重下」，所以下载链必须有断点续传与字节校验。 |

### 1.2 设计目标

本工程的设计围绕上述失效模式组织，而不围绕站点数量组织。

| 维度 | 问题 | 本工程的回答 |
|---|---|---|
| 抓取 | TLS 指纹、JS 挑战、行为检测 | 五级回退调度（§3.1） |
| 解析 | 站点形态各异 | 通用正文抽取 + 声明式站点规则 + 内嵌 JSON 解析（§4.1） |
| 数据质量 | 重复、空壳、隐私混入 | 内容指纹去重 + 质量评分闸 + 三层脱敏（§3.5） |
| 稳定性 | 并发、长跑、挂死 | 租约 + CAS + 两级令牌桶 + 看门狗 + 断点续传（§3.2–§3.7） |

### 1.3 非目标与显式拒绝

单机定位是产品决策而非能力缺陷：它换来零部署、零服务端维护与数据不出本机。相应的拒绝项在开篇写明，每项都带理由。

- **不做多用户与多租户**。配置、凭据与数据布局都假定「一人一机」；多租户要重做的是整个凭据与数据模型，不是加一个登录页。
- **不做分布式抓取集群**。前沿队列的租约语义是为单机多协程设计的；横向扩展需要另一套队列协议，硬扩会把 §3.2 的一致性保证变成纸面文章。
- **不碰账号权限内的内容**。登录态只来自使用者自带的 cookies，拿不到就如实报错而不是绕路。这是产品立场而非技术限制：工程解决的是「公开内容怎么稳定拿到」，不是「权限墙怎么翻」。
- **不默认启用大模型增强**。相关能力默认关闭，需要者显式开启；这避免了「不装模型就跑不了」的依赖倒置。
- **不落盘未脱敏的个人信息**。手机号、邮箱、IP 在落盘前即被脱敏（§3.5）。这是默认行为，只有命令行显式传 `--no-sanitize` 或使用界面上的对应开关才会关闭，且界面会记录该选择。

## 2 系统概览

### 2.1 规模与交付形态

| 构成 | 规模 |
|---|---|
| 引擎（`kiana_vnext_plus/`） | 71 个 Python 模块，27,620 行 |
| 桌面界面（`launcher_v9.py`） | 3,652 行，PySide6/qfluentwidgets 五页 FluentWindow |
| 测试 | 约 1,490 个用例，全部离线 |
| 依赖 | 运行时 25 条 + 开发 6 条，全部 `==` 钉死版本 |
| 站点规则 | 14 条声明式 YAML——12 条生产规则各配套真实页面样本，另 2 条为模板 |
| 存储 | SQLite：10 张业务表（队列 8 张 + 导出 2 张）另加 1 个 FTS5 索引；`PRAGMA user_version` 幂等迁移（当前 schema 版本 6） |
| 交付 | 双 exe（PyInstaller onedir）+ NSIS 多语言安装器，实测约 622 MB |

交付体积是刻意的取舍：浏览器内核（Chromium）、ffmpeg、PO Token 的 Node 服务与 deno 运行时全部随包分发，换来「装完即用、运行期零下载」。`docs/BUILD.md` 记录了安装后约 1.8 GB 的磁盘占用。这笔账的代价由每一次下载安装包的人和必须核对随包组件的发布流程承担；收益是第一次抓取与第一千次行为一致。两个 exe 分工明确：`KianaLauncher` 是含进程内引擎的五页界面壳，`KianaCrawler` 是面向脚本化与无人值守的命令行形态；两者共享同一个引擎包，差异只在控制面——命令行参数与界面设置最终翻译为同一份引擎配置。

### 2.2 进程模型：引擎不是子进程

`EngineBridge` 在一个 daemon 线程里运行独立的 asyncio 事件循环，进程内直接调用引擎入口 `crawl()`；`print` 与 `logging` 两条输出被桥接为 Qt 信号。收益是任务状态免序列化直读——暂停、恢复、停止都是函数调用而不是消息往返，单进程断点能走全栈，打包产物也不需要进程间协议。代价是一条必须严守的纪律（**界面不允许直接触碰引擎对象**，只能经由桥的 stop/pause/resume 三个控制口与只读引用），以及跨线程回主线程必须走 `QApplication.postEvent` 而非信号直连。两条规约都来自真实事故。这个选择的后果是不对称的：子进程架构下引擎崩溃只损失一个子进程，进程内架构下它会带崩整个窗口，因此桥必须捕获每一类引擎失败并翻译成有文档的退出码。

退出码是固定契约：0 正常完成、1 使用者主动停止、2 引擎崩溃、3 引擎加载失败。界面与任何脚本化封装消费同一套语义。

### 2.3 一次抓取的完整路径（17 步）

建立段（1–3）：创建任务目录（`cli_<sha8>/`，内含队列库、导出树、统计流 `stats.jsonl`、断点 `checkpoint.json` 与日志）→ 种子 URL 分流 → 入队。执行段（4–12）：取批（写租约）→ 取出口与并发名额 → 心跳续约 → 缓存命中判定 → 五级路由 → 解析炸弹闸 → 脱敏 → 去重 → 质量闸。出口段（13–17）：CAS 认领 → 持久化与导出 → 媒体入队 → 出链发现 → 统计。

每一步都有明确的失败分支：取批失败进死信，路由逐级升级，CAS 失守一字不写，看门狗到点击杀超时页而不连累同批其他页。

### 2.4 运行期数据布局与凭据治理

运行期数据根由 `config.data_root()` 决定：默认 `%LOCALAPPDATA%\KianaVnextPlus`；设置 `KIANA_PORTABLE=1` 时切换为 **exe 同级**的 `KianaData/`。便携根**不得**取 `sys._MEIPASS`：在 PyInstaller onedir 布局下它指向 `_internal`，而卸载器会用 `RMDir /r` 清理 `_internal`，数据根放在那里意味着升级即丢数据；exe 同级目录不受卸载清理影响。

凭据治理遵循一条原则——本机密钥不出本机。使用者提供的 cookies 经 `cookie-add` 子命令加密入库（Fernet，`cryptography` 提供）；主密钥落盘为受 DPAPI 保护的 `master.key.bin`；密钥文件名形态与便携数据根都在 `.gitignore` 与门禁第 6、7 两项（密钥形态扫描、凭据字面量）的看守之下，未跟踪的构建产物同样算脏。`cookie-list` 可查看已入库账号的健康状态。程序侧没有任何内置凭据，示例一律使用能通过扫描的占位符。HTTP 缓存落盘的内容是脱敏后的（§3.5），因此缓存目录不构成二次泄漏面。

## 3 关键机制

### 3.1 可达性层：五级回退

`engine_router.py` 按代价从低到高排布五级：协议通道（curl_cffi 的 TLS 指纹模拟）→ 隐身通道（源码级反检测）→ TLS 切换 → 真浏览器（patchright 主通道、playwright 兜底）→ 直连。前一级失败或撞上挑战时请求自动升级；低成本通道能拿到内容时，浏览器进程根本不会被拉起，这是并发下「浏览器风暴」不会发生的原因——渲染另有独立的预算上限。阶梯的代价是各层必须彼此一致，因此「UA 与 TLS 同源绑定」只存在于一个选择函数里，而不是每层各写一份。

两个设计细节是承重的。其一，**拦截与升级使用不同的信号**：被闸拦下的请求返回 400，而 403 被保留为「升级到浏览器层」的信号——混淆两者会让被拦截的 URL 跑进注定失败的浏览器渲染。其二，**隐身通道不做 JS 注入**：运行时属性伪装会留下可检测痕迹，本工程走协议层修复与启动参数治理（patchright 提供 Runtime.Enable 泄漏修复），并显式区分「删 stealth」与「删 UX」两类改动。

回退调度的上游还有三个可选开关，各自对应一类合规或效率诉求：`--robots` 在链接入队前按域判定 robots.txt 合规；`--sitemap` 开启站点地图播种，把「给一个入口、抓全站结构」变成一次声明；cookie 库（§2.4）为需要登录态的页面提供凭据，凭据不足时按可读原因降级。这三个开关都不改变回退语义——它们决定哪些 URL 值得进入回退调度，回退调度决定取回它要付多少代价。

### 3.2 一致性层：租约与比较交换

前沿队列 `frontier.py` 是 SQLite 上的 8 张表，用 `PRAGMA user_version` 幂等迁移到版本 6；导出侧另有 2 张表与 1 个 FTS5 索引（§2.1）。并发正确性建立在两个原语上。

**租约**。取任务即写入 `leased_at` 与 `lease_expires`；60 秒心跳续的是 `lease_expires`，**不是** `leased_at`——改后者会破坏 CAS 闭环。独立的到期列来自一次真实缺陷：单页最坏处理时长超过租约超时后，页面在仍被处理时就被回收重发，同一个 URL 上出现两个协程，媒体与导出各留一份。

**CAS**。结果落盘前必须赢一次比较交换，且它是三态的：赢（写入）、输（一字不写）、**数据库故障**（`None`，必须抛出并重试；把 `None` 当作「输了」会让锁库故障被静默吞掉）。失败路径同样有守卫：`mark_failed` 的 UPDATE 必须带 `AND status != 'done'`，否则看门狗会把已完成落库的页面打回重试，造成整页重爬与重复导出——这是真实发生过的缺陷，现为回归用例。

`database is locked` 与「租约易主」是**两类事件**，不能共用一个分支：前者是 SQLite 写锁冲突，靠 `busy_timeout` 等待或抛出重试；后者是另一个 worker 已合法接管任务。CAS 的三态设计正是为了让这两类事件不可能被同一个 `else` 吞掉。

死信是这套协议的最后一级：重试次数耗尽、或限流计数越限的页面进入死信而非无限滞留，任务因此**总能结束**。结束不等于全部成功，而是每种结局都有归属。死信页携带失败原因分类，`retry-dead` 可以把它们成批重新入队（例如换一批出口 IP 之后），`errors` 则聚合失败分布——长跑任务的健康度因此可量化，而不是一个含混的「跑完了」。

竞态防控有一条统一规约：**跨 `await` 的读-改-写就是真竞态，正确写法是「同步块内先占位再 await」**。robots 门闸与渲染预算都按此实现。

### 3.3 流控层：两级令牌桶与可终止的重试

限速是全局与按域的两级令牌桶，但它最重要的设计不是桶本身，而是**重试语义的切分**：被限流（throttled）不消耗重试预算。限流走独立的计数器，连续多次后转死信；真正的传输失败才递增 `retry_count`。没有这个切分，限流期间任务会永驻重试队列，主循环的退出条件永远无法成立——任务「跑不完」而不是「跑得慢」。

与它并列的还有一层**传输语义的切分**：传输异常必须抛出，而「被闸拦下／协议非法」才返回空值。两者混同的后果，要么是把一次网络抖动当成永久失败而丢掉可重试的机会，要么是把一次确定性的拦截当成可重试的故障而一路重试到死信。调用方据此靠 `except` 决定重试，靠返回值决定放弃。

并发在三级之间仲裁——全局、按域、按出口，取最小值。每域默认 20 路，每出口默认 10 路；全局上限按机器自适应为 `max(8, min(32, 2 × 逻辑核数))`，除非显式配置——这避免了机器直接沿用配置里的占位值。控制器停止/恢复时必须归还诉求并重算，否则一次风控降级留下的低值会永久钳死并发（本工程已修过一次）。`Retry-After` 头遵守但封顶 300 秒，防止单个站点用一个头把整批任务挂起数小时。

### 3.4 出口安全层：逐跳 SSRF 防护

这是本工程代价最高的一课：**只在入口校验 URL 是不够的**。一个外部图片地址可以返回 302 指向内网，底层 HTTP 库会自动跟随——用两个回环服务在本机复现了「内网响应被当作图片正常落盘」。因此所有出网取流必须经过 `url_utils.py`，全仓被引用最多的模块。

之所以收口到**一个共享原语**而不是各通道自建校验，是因为安全检查的失效模式恰恰是「漏了一处」：引擎里有主抓取、媒体下载、m3u8 分片、链接发现多条出网路径，任何一条自建校验都会在未来某次改动里被遗忘。共享原语使「新增出网路径默认安全」，绕过原语反而需要刻意写出一行非常规代码——这在评审里是一眼可见的。

- **入口校验 + 关闭自动重定向 + 逐跳复检**。curl_cffi 默认跟随 30 跳重定向且其响应对象没有 `.url` 属性，复检落点只能靠手动逐跳实现。
- **主机名规范化**：IPv6 zone id 与 FQDN 尾点都曾被用来绕过黑名单，先归一再判定。
- **25 条对抗性私网样本**进入回归套件，覆盖十进制、十六进制、八进制 IPv4 写法、IPv4 映射的 IPv6、CGNAT、6to4 中继段与云元数据主机名——这些形态标准库自带的判定并不覆盖。
- **DNS 判定 90 秒过期**：阻断「首次解析到公网、稍后改指内网」的 rebinding 手法。
- **重定向上限 10 跳**。

这一层的代价真实且落在热路径上：重定向要手动跟、每一跳都要复检、DNS 判定缓存需要自己的过期策略（既不能放过 rebinding 窗口，也不能每页都查一次）。一个反直觉的例外被显式记录：`llm_client` 不套闸——那里是使用者自填的本地推理端点（例如回环上的 Ollama），套闸会把本地服务拦死。安全机制可以允许有理由的例外，但理由必须写在注释里。

### 3.5 数据卫生层：三层脱敏与显式边界

脱敏覆盖三个泄漏面。**日志**：过滤器挂在 handler 上——Python logging 只调用祖先的 handler、不调用祖先 logger 的 filter，挂在 root logger 上等于没有；新建 handler 由被包装的 `logging.Handler.__init__` 自动获得脱敏。**旁路**：print 桥、界面日志、异常回显各自过一遍。**产物**：导出副本经 `sanitize_record` 逐记录脱敏，递归 6 层。共覆盖 19 类敏感 URL 参数（`token`、`key`、`sign`、`session`、`csrf` 等）与手机号、邮箱、IP 模式；HTTP 缓存落盘的内容也是脱敏后的。

参数识别走**显式清单而非泛匹配**。像「参数名含 key 就删」这样的泛匹配，误杀率不可控，会把业务参数一并抹掉；显式清单的代价是新型参数需要补录，但每一条都在评审之下。这与 §3.4 用穷举的私网形态而非正则推断是同一个取舍：宁可漏一点，不可错一片。

**边界同样被显式写下**：任务队列里的 URL 不脱敏。它们是「稍后还要再请求一次」的钥匙，抹掉签名参数会让续爬直接 403。这条「哪里绝不脱敏」的推理写在代码注释与回归用例里，防止后来者出于好意「顺手补闸」把功能改坏。

导出格式侧还有一个字节级的边界案例：CSV 的 UTF-8 BOM **只允许在新文件首次写入时出现一次**，追加模式不得使用 `utf-8-sig`——否则每次追加都会再写一个 BOM 到文件中部，从第二批数据起整列被污染。这曾是真实缺陷，现为回归用例。

### 3.6 媒体层：直链解析与无损下载

四个平台解析器（抖音、小红书、快手、网易云）通过一张域名表分派。解析策略是**先读页面已有的数据**（`window.__INITIAL_STATE__`、JSON-LD），而非凭空构造请求参数。产物统一收敛到 `MediaItem`（`source / media_id / kind / streams / images / method` 等字段），上层只认一个 schema，不需要知道四个平台各自的响应结构。签名算法（如抖音 a_bogus 的 SM3 链路）按公开协议事实实现，配逐字节固定向量做回归——实现漂移因此能在提交前被拦住，而不是等站点改了返回才暴露。

两条硬约束挂在接入协议上：解析器是纯同步实现，必须经 `asyncio.to_thread` 调用，否则冻结整个事件循环（抖音曾因此冻结 30–80 秒）；解析出的直链来自远端页面状态，属于受外部影响的输入，必须过 `is_private_url` 复检——这正是 §3.4 的闸在媒体通道上的延伸。

下载器保证**无损与原子**：先探测总大小与 Range 支持，流式写 `.part`，按字节偏移续传，按字节数自校验，最后原子改名——下游永远看不到半截文件。m3u8 分片含 AES-128 解密（pycryptodome）；ffmpeg 只用于合并分片，**不做任何重编码**；服务端不支持 Range 时弃旧 `.part` 重下，绝不拼接出坏文件。视频是字节搬运；音频仅在显式开启音频通道时转 MP3。可选组件遵循同一条原则：**可选能力缺席不构成故障**——B 站弹幕的 ASS 转换在组件未安装时自动跳过，弹幕数据本身照常采集。

### 3.7 存活层：看门狗、阻塞卸载与两类 Windows 静默失败

单页看门狗默认 300 秒（正常页 < 60 秒，5 倍余量），可配置，可用 `--page-timeout 0` 显式关闭——v2.19.8 修复了该参数「传了也不生效」的透传缺陷。超时页被击杀并标记重试，不连累同批其他页。余量本身就是取舍：挂死的页面最多要花五分钟才被回收，这是「不误杀合法的慢页面」所付的价。

与看门狗配套的是一条全仓纪律：**阻塞调用一律 `asyncio.to_thread`**——SimHash 指纹、全文脱敏、文件 IO、同步解析器全部在内；事件循环里不允许出现会阻塞的调用。

Windows 上另有两类静默失败，各有固定解法，因为两者都不抛异常。**子进程编码**：yt-dlp 调 ffmpeg 时，子进程输出按系统代码页解码，中文文件名会让合并失败、甚至留下一个空文件夹；解法是文件名改为 ASCII 哈希、并为子进程强制 UTF-8 区域设置。**非 ASCII 路径读图**：`cv2.imread` 在 Windows 上遇到非 ASCII 路径会返回 `None`（不抛异常），壁纸管线因此改用 `np.fromfile` 读字节、`cv2.imdecode` 解码。两者的共同点是失败模式安静——没有异常、没有日志——下一个维护者会以为功能是坏的，而代码其实是好的。

### 3.8 可观测性与可恢复性

长跑任务必须回答两个问题：现在在干什么，断了能不能接上。可观测性方面，统计经 `stats.jsonl` 以追加流落盘，界面统计卡与 CLI `status` 子命令消费同一份契约；失败与错误档案经 `errors` 子命令聚合，「这次跑了多远、坏在哪类站点」因此可回答。可恢复性方面，任务目录里的 `checkpoint.json` 记录断点，失败页可从死信状态用 `retry-dead` 重新入队而不必从头再来，队列本身持久于 SQLite，导出树按域名分目录落盘（JSONL / CSV），媒体按类型归档——任务目录是自包含的，可以整个拷走分析。

这套设计的取舍是「文件优先」：不引入额外的观测服务或数据库依赖，一切状态都是可直接打开的文件。对单机工具，一个能立刻打开的 `stats.jsonl` 比一个要先起服务才能看的面板更可靠，诊断在离线的机器上同样可行；代价是没有实时看板，也没有跨机器的聚合。

## 4 扩展模型

### 4.1 声明式站点规则

加一个站点不改代码：写一条 `rules/sites/<域名>.yaml`，用 `rule-new` 生成骨架、`rule-validate` 校验、`rule-test` 对本地样例试跑——三个子命令构成「编写-校验-回归」闭环，全程离线。树内 14 条规则文件中，12 条是生产规则，每条配套一份从真实页面抓取的 HTML 样本，发版门禁核对样本清单（登记的 12 个站点域样本齐备）；余下 2 条是模板。规则约定了 `exclude` 键，把导航、广告、播放页之类的 URL 排除在正文抓取之外，避免与视频、音乐通道互相抢任务。

由此得到的性质是：规则层的回归不依赖任何实时站点——站点改版不会让测试套件连夜变红，而是由实站回归线（门禁第 9 项）单独暴露。代价是每条规则都要把抓取到的样本作为仓库产物带上，而样本会过期——这正是结构指纹检查（§5.2）存在的理由：它能发现样本被替换、被截断或被改坏编码。

### 4.2 平台解析器接入协议

新平台 = 新建一个返回同构 `{ok, ...}` 字典并经 `media_schema` 收口的模块 + 在分派表加一行 + 视需要加入国内直连名单 `exit_manager._DOMESTIC_DOMAINS`（63 条原始条目、去重 59 个）——名单的存在是因为海外代理 IP 访问国内站点会触发风控，B 站的极验挑战是实测案例。

「同构 `{ok, ...}` 字典」是这条协议承重的部分：解析器的失败也是数据（`ok: false` 加原因），不是异常，下载链因此可以把「该平台没帮上忙」当作「保持原 URL 走通用通道」的理由，而不是让一个平台的故障打断整批任务。直链截取同样走 schema（优先 `media.streams[0].url`，退回平台历史键），调用方不需要知道各平台自己的响应结构。结果是「新增平台」的代码量稳定在一个文件加一行，并且两条硬约束（`to_thread`、私网复检）写在接入契约里，而不是依赖扩展者的记忆力。

### 4.3 配置一致性：六点接线

界面的一个设置项要经过六个环节才能生效：控件创建 → 接线 → 启动配置 → `EngineBridge` 翻译表 → `crawl()` 的显式键表 → `DEFAULT_GLOBAL` 默认值。**漏掉任何一环都等于「能填不生效」，且不报错**——这就是把清单写下来并逐点核对的原因；`--page-timeout` 直到 v2.19.8 才走通全部六环。

配置系统有一条贯穿性原则：**`DEFAULT_GLOBAL` 是引擎默认值的唯一来源**。界面层（`launcher_config.json`）与引擎层各持一份配置，桥的翻译表只做「界面键 → 引擎键」的搬运；默认值不许在两处各写一份，否则改一处漏一处，同一参数在不同入口下行为不同。`page_timeout_override()` 做成纯函数也是同一个理由：把「只有显式指定才覆盖」的判定收敛到一个可单测的位置——命令行不传时返回空、引擎回落 300 秒；显式传 0 时无条件透传，看门狗真正关闭。「未指定」与「显式为零」从此是两个可区分的状态，而这是事故复盘时最容易被误判的一类缺陷。

### 4.4 界面工程：五页控制台与壁纸管线

桌面界面共五页（首页、日志、数据、任务、设置），构建在 qfluentwidgets 的 `FluentWindow` 之上。两条纪律来自事故。其一，**页面构建只在 `__init__` 执行一次**：一次缩进事故曾让桥接与页面构建落进尺寸变化处理函数里，于是每次显示、缩放与窗口激活都会重建桥、五个页面、导航项与应用主题——仅主题一项就要遍历约 1,910 个控件、每次约 1.2 秒。修复后重建成本为零。其二，**统计卡必须显式注册**：早期实现用 `findChildren` 按对象名扫描控件树，树一变就出现「接好了但不更新」且无任何报错；现改为显式注册表，漏注册在评审时肉眼可见。

壁纸管线是界面里最重的一块图像处理：单张与文件夹轮换、封面裁切（九宫格焦点控制偏移）、0–30 档高斯模糊、基于亮度分析的自动蒙层（亮图多蒙）、两层交叉淡入淡出，以及从壁纸提取强调色（HSV 过滤后取直方图众数，可锁定为手选色，与取色模式互斥）。参数变更走 200 毫秒防抖并按 `(路径, 尺寸, 模糊, 蒙层, 焦点)` 做结果缓存，缩放不会重复计算重采样；重活全部在 `to_thread` 中执行，Qt 图形对象只在主线程构造。右下角的电子签名水印默认**为空**：程序不内置任何默认文案，是否落款、落什么款完全由使用者自填。

## 5 质量保障体系

### 5.1 离线测试线

约 1,490 个用例（1,483 个测试函数，其中 3 个带参数化）全部离线——测试套件不发起任何真实网络请求；站点规则以真实页面 HTML 样本为 fixture，签名算法以固定向量为断言，并发一致性以内存库为靶子。离线是设计选择而非妥协：需要实时站点才能跑的套件无法充当门禁。全量测试的通过判据被门禁固定为「≥400 passed 且 0 failed」。

测试套件按交付批次组织（`test_v218_*`、`test_v219_*`、`test_v2198_*`），每个批次对应一次版本交付引入的机制与修复的缺陷。这样组织的收益是**可追溯**——看到一条失败用例的文件名，就知道它守护的是哪一批机制；也便于在重构时判断哪些用例承载不变式、哪些只是当时的实现细节。依赖特定环境（浏览器内核、Node 运行时、实站求解器）的用例按条件跳过，跳过机制本身也被门禁的计数口径覆盖。

### 5.2 十四项发版门禁

`python tools/release_check.py` 一次跑完十四项，任一失败即禁止发版。前十项是原有的发版清单；后四项是在连续几轮复核暴露出「整类缺陷根本没有检查」之后补上的。

| # | 检查 | 它确立的事实 |
|---|---|---|
| 1 | 版本一致性 | `VERSION.json`、`pyproject.toml`、`__init__.py`、NSIS 脚本四处一致 |
| 2 | Git 卫生 | 工作区干净；未跟踪文件也算脏 |
| 3 | 全量测试 | ≥400 passed 且 0 failed |
| 4 | 静态检查 | ruff 80、mypy 99，上限锁死为 80 与 99；另加 `tools/` 与 `tests/` 的 F 类（真缺陷）子集 42；锁死的基线只许降不许升 |
| 5 | 依赖审计 | pip-audit 对钉死版本比对漏洞库（本版：无已知漏洞） |
| 6 | 密钥扫描 | 分发面内无私钥或可用 API key 形态 |
| 7 | 凭据卫生 | 仓库零 cookies 与凭据字面量；`.gitignore` 覆盖 cookies 产物 |
| 8 | 规则与资产完整性 | 14 条规则全部加载；登记的 12 个真实站点样本齐备 |
| 9 | 实站回归 | `verify_all` 跑多条探针线，判定只取其总体结论行 |
| 10 | 构建面 | 入口可编译、spec 存在；PO Token 缺件会在打包期硬中止 |
| 11 | 结构指纹 | 样本结构指纹与入库基准逐一比对；离线部分永远跑，在线部分数不出来时返回退出码 2 记为 SKIP，绝不冒充 PASS |
| 12 | 静默失败扫描 | 热路径上无理由注释的 `except: pass`，对锁死基线只许降不许升 |
| 13 | 脱敏链路 | 往新 handler 打含特征串的日志（URL 签名参数、Cookie 头、邮箱），判据是输出里真的搜不到 |
| 14 | 同一能力多份实现 | 跨模块同名函数而形参不一致者阻断发版；出现在三个及以上模块的名字只做登记 |

门禁的设计哲学可以概括为一句话：**把「发布前应该检查的事」变成「发布前必须通过的事」**。它的每一项都对应一种单人项目特有的失效方式——版本号改了四处漏一处、工作区留着未跟踪的调试产物、静态告警悄悄回升、密钥随手写进示例、规则加了样本没加。门禁不提供「跳过但警告」的中间态：FAIL 即退出码 1，SKIP 必须显式声明理由（如 `--skip-network`）。把静态基线锁成「只许降不许升」是其中最反直觉也最有效的一项：它不要求代码完美，只要求**不要比昨天更糟**——对单人维护的仓库，阻止回退比追求完美现实得多。代价是每清理一批就要重新标定基线，以及「数不出来」的检查会如实报 SKIP 而不是绿。

### 5.3 依赖治理与供应链

25 条运行时依赖 + 6 条开发依赖全部 `==` 钉死；升包必须重跑门禁并按需重新标定锁死的静态基线。许可逐项盘点：两个 GPLv3 组件（GUI 框架与 PO Token 插件）决定了工程整体按 GPL-3.0 授权（§8）；随包字体与插画另有来源与许可声明。GitHub Actions 在 Windows runner 上复跑版本一致性、静态检查、全量测试与覆盖率报告，覆盖率只报告不设阈值（§7）。两条边界值得写明：这份钉死的依赖组合是在单机验证过的配置，而不是跨 Python 版本的矩阵；CI 只覆盖可离线执行的部分，打包与实站回归仍是手工步骤。

### 5.4 构建与发布工程

发布链路由一个脚本 `一键构建.bat` 串起七个编号阶段与三个子阶段：解释器检查（1）、依赖核对（2）、Chromium 下载（3）、语法检查（4）与静态检查（4c）、行为测试（4b）、PO Token 组件检查（4d）、双 PyInstaller 构建（5）、NSIS 打包（6）、产物归档（7）。两个 spec 分别对应两个 exe——`KianaCrawler.spec` 是命令行形态，`KianaLauncher.spec` 是五页界面壳——两者共享同一个引擎包，spec 只决定入口与资源收集面。

构建侧的硬约束同样来自事故：

- **PO Token 组件缺件会硬中止构建**。spec 检查 vendor 目录（Node 服务与 deno 运行时），缺件直接 `raise SystemExit`；逃生舱 `KIANA_SKIP_POT=1` 只留给测试构建。理由是曾经「静默打包成功、装出去才发现组件缺失」。
- **打包后强制产物完整性检查**：`_internal` 下必须找到 deno 可执行文件、PO Token 服务入口与浏览器二进制，任一缺失即判构建失败。
- **qfluentwidgets 的资源文件必须随包收集**（`collect_data_files`），漏掉的症状是打包后界面白屏——它带 SVG/QSS/字体资源，纯代码收集看不见它们。
- **NSIS 安装器的语言文件是生成物**（由 `tools/gen_nsis_langs.py` 生成，禁止手改）；卸载器是**三分支条件逻辑**：注册表安装且可恢复 → 恢复原安装；注册表安装且不可恢复 → 彻底清理；无注册表 → 只删自身。快捷方式恢复分支曾因 NSIS `CreateShortCut` 取当前 `$OUTDIR` 作起始位置，把恢复出来的快捷方式指进临时目录，v2.19.8 以 `SetOutPath` 显式重定到被恢复的安装目录修复。
- **在 Git Bash 里调 makensis 必须经 Python subprocess**：MSYS 会把 `/S` 一类的开关改写成 `S:/` 路径。
- **安装/卸载矩阵工具**（`tools/installer_matrix.py`）覆盖 8 个语言 ID，逐语言描述安装、校验、卸载三段流程；`--dry` 在任何系统改动之前短路——这条很重要，因为「传了 --dry 却仍然真装真卸」会动到使用者机器上那份真实安装。

### 5.5 回归用例：从事故到断言

这套测试不是按覆盖率凑数，而是**每条真实事故固定为一条回归用例**。代表性样本：

| 事故 | 回归断言 |
|---|---|
| 风控降级后全局并发被永久钳死（恢复的控制器不归还诉求） | 恢复后 min-wins 诉求必须归还 |
| 看门狗把已完成落库的页打回重试（整页重爬 + 重复导出） | `mark_failed` 带 `status != 'done'` 守卫 |
| `database is locked` 被当作租约易主静默吞掉 | CAS 三态：`None` 必须抛出 |
| 被限流的任务永驻重试队列，主循环永不退出 | throttled 不递增 `retry_count`，走独立死信计数 |
| CSV 追加写入 BOM 污染第二批数据 | BOM 仅在新文件首写时写一次 |
| 裸 `session.get` 跟随 302 把内网响应存成图片 | 25 条对抗性私网样本全部拦截 |
| 解析器直链漏过私网复检 | 媒体通道直链必经 `is_private_url` |
| `--page-timeout 0` 传不进引擎 | 显式值（含 0）无条件透传，0 可关看门狗 |

这张表是第 3 节各机制存在的原因——机制不是设计出来的，是事故逼出来的，然后用例钉住。新贡献者读测试时可以把这张表当作索引：每条断言背后都有一个「如果没有它会再次发生」的故事。

## 7 已知边界与未决项

以下各项按原样陈述，不做修饰。

1. **部分平台解析器仅有离线证据**：没有对实时服务的端到端验证；缺登录态时按可读原因降级，而不是绕路。缓解方式是实站回归线（门禁第 9 项），它把「取不到」如实记为 SKIP 而不是成功。
2. **少数实站解析当前失败**，原因尚未定位；在定位前保持为未决项，不断言是平台侧变更。`errors` 子命令是定位所需的证据来源。
3. **安装包 622 MB** 偏大——这是「运行期零下载」的代价（§2.1）；缓解是一次交付加三分支清理的卸载器（§5.4），而不是把包做小。
4. **覆盖率只报告不设阈值**：CI 发布覆盖率报告，未配置任何阈值。理由是本套用例的主要来源是事故回归而非行覆盖，行覆盖率在当前阶段不是有效质量信号。
5. **大模型增强默认关闭**。
6. **单人维护**是工程事实：十四项门禁与锁死的静态基线是对这个现实的工程回应，而不是否认它；全部机制与陷阱都写在仓库内（本文档、`docs/ARCHITECTURE.md`、`docs/BUILD.md`、`tools/`），交接不依赖某一个人的记忆。

## 9 结论

kiana-crawler 的工程价值不在于功能清单的长度，而在于**每个声称都有出处、每个边界都被写出**：五级回退对应五种真实的拦截手段，租约与 CAS 对应两类真实发生过的并发事故，逐跳闸对应一次本机复现的攻击，十四项门禁对应单人维护的各种失效方式。压缩成一段话：这个工程把「个人项目」最常见的三种死法——静默的并发故障、静默的安全漏洞、静默的「能填不生效」——各自做成显式契约（CAS 三态、逐跳闸、六点接线），再用一条「任何一项失败就禁止发版」的门禁把契约钉住。它的可信度不来自承诺，而来自**打开仓库五分钟内就能复核本文任何一句**。对一位在 Windows 上需要一台「装完即用、行为可预期、产物干净」的采集机的使用者，这是一个可以被逐条验证的答案；对其余场景，§1.3 与 §7 给出了诚实的「不」。对工程实践有兴趣的读者，`tools/release_check.py` 与 `tests/` 是比本文更好的起点：机制在代码里，事故在用例里。
