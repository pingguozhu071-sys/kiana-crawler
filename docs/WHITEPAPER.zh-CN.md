## 摘要

现代网页对自动化采集布置了多层防御：传输层的 TLS 指纹识别、执行层的 JavaScript 挑战、行为层的频度与轨迹检测；媒体类站点则把可直接下载的资源封装在带时效签名的页面内嵌数据中。在"单机、单人、无服务端"的约束下同时解决这些问题，并且不牺牲数据质量与长跑稳定性，是本工程要回答的问题。本文按论文体陈述 kiana-crawler 的设计与实现：以五级回退调度解决可达性，以租约加比较交换（CAS）的一致性协议解决并发正确性，以逐跳校验解决服务端请求伪造（SSRF）风险，以三层脱敏及其显式边界解决数据卫生，以两级令牌桶与看门狗解决长跑稳定性；并给出由离线测试线（675 个用例）与十项发版门禁构成的质量保障体系。文中全部量化陈述均可对照仓库源码复核（附录 A 给出索引）。

**关键词**：网页采集；反爬对抗；并发一致性；SSRF；数据脱敏；断点续传；发布工程

**读者与用法**：如果你在决定"要不要用、要不要读它的代码"，先读 §1 与 §7——边界清单比功能清单更值得先看；如果你想评估工程质量，§3 与 §5 是主线，每节末尾的关键数字都能在附录 A 找到复核方式；如果你准备为它贡献代码或规则，§4 的三份接入契约与 §5.4 的构建约束是必读项。

## 1 引言

### 1.1 问题域

从一台普通 Windows 机器上稳定地采集公开网页与媒体，2020 年代中期至少要跨过四道坎：

1. **可达性**。站点用 TLS 指纹识别非浏览器客户端，用 JS 挑战过滤不执行脚本的请求，用行为检测拦截高频访问。任何单一策略都无法同时覆盖三种防御：能过 TLS 校验的客户端未必能执行挑战，能执行挑战的真浏览器又代价高昂。更麻烦的是防御是**组合**出现的——一个站点可以同时上 TLS 指纹与挑战，这意味着采集端必须能把多级手段按代价排序、按需升级，而不是在"全用重炮"与"全用轻弹"之间二选一。
2. **正确性**。几十路协程并发处理同一批 URL 时，经典并发故障——同一页被处理两次、结果被互相覆盖、数据库写入交错——会在无人干预的情况下静默发生。静默是这类故障最坏的性质：它不崩溃、不报错，只在几天后被人发现产物里有两份一样的页面，或队列状态与磁盘事实不一致。
3. **数据卫生**。产物中混入重复内容、空壳页、他人手机号邮箱或 URL 中的会话令牌，是会真实伤害使用者的缺陷；而脱敏本身又有边界，脱错位置会直接破坏功能——把队列里稍后要再请求的 URL 脱了签名，续爬就是 403。
4. **稳定性**。一个挂死的页面可以拖住整批任务；一个设计不当的限速器会把重试变成永不终止的风暴；一次网络抖动若被当成永久失败，长跑任务的完成率将永远到不了 100%。

媒体站点在这四道坎之上再加一层：播放地址藏在页面内嵌 JSON 里，带时效签名，直接把页面 URL 交给通用下载器往往拿不到最高画质——而"换个清晰度重下"对大文件是不可接受的浪费，下载层必须有断点续传与字节校验。

### 1.2 设计目标的四元分解

本工程的设计不围绕"支持更多网站"展开，而围绕上述四个问题组织：

| 维度 | 问题 | 本工程的回答 |
|---|---|---|
| 抓取 | TLS 指纹、JS 挑战、行为检测 | 五级回退调度（§3.1） |
| 解析 | 站点形态各异 | 通用正文抽取 + 声明式站点规则 + 内嵌 JSON 解析（§4.1） |
| 数据质量 | 重复、空壳、隐私混入 | 内容指纹去重 + 质量评分闸 + 三层脱敏（§3.5） |
| 稳定性 | 并发、长跑、挂死 | 租约 + CAS + 两级令牌桶 + 看门狗 + 断点续传（§3.2–§3.7） |

### 1.3 非目标

单机定位是产品决策而非能力缺陷，它换来的是零部署、零服务端维护与数据不出本机。相应地，以下几项被明确排除，且每项排除都有对应的理由：

- **不做多用户与多租户**——单机工具的配置、凭据与数据布局都假定"一人一机"，多租户需要重做的是整个凭据与数据模型，不是加个登录页。
- **不做分布式抓取集群**——前沿队列的租约语义是围绕单机多协程设计的，横向扩展需要的是另一套队列协议；硬扩会把 §3.2 的一致性保证变成纸面文章。
- **不碰账号权限内的内容**——登录态只来自使用者自带的 cookie，拿不到就如实报错。这不是技术限制而是产品立场：工程解决的是"公开内容怎么稳定拿到"，不是"权限墙怎么翻"。
- **不默认启用大模型增强**——LLM 相关能力默认关闭，需要者显式开启；默认关闭避免了"不装模型就跑不了"的依赖倒置。
- **不采集个人信息**——联系方式、邮箱、IP 在落盘前即被脱敏（§3.5）；这不是可选项而是默认行为，只有使用者显式传 `--no-sanitize` 才会关闭，且界面有对应开关记录该选择。

## 2 系统概览

### 2.1 规模与交付形态

| 构成 | 规模 |
|---|---|
| 引擎（`kiana_vnext_plus/`） | 67 个 Python 模块，22,635 行 |
| 桌面界面（`launcher_v9.py`） | 1,645 行，PySide6/qfluentwidgets 五页 FluentWindow |
| 测试 | 675 个用例（674 通过 / 1 跳过 / 0 失败），全部离线 |
| 依赖 | 运行时 25 条 + 开发 6 条，全部 `==` 钉死版本 |
| 站点规则 | 12 条声明式 YAML，每条强制配套真实页面样本 |
| 队列存储 | SQLite，8 张表，`PRAGMA user_version` 幂等迁移（当前 schema 版本 5） |
| 交付 | 双 exe（PyInstaller onedir）+ NSIS 多语言安装器，实测约 542 MB |

交付体积值得说明：浏览器内核（Chromium）、ffmpeg、PO Token 的 Node 服务与 deno 运行时全部随包分发，换来的是"装完即用、运行期零下载"。这是用 542 MB 的安装包换部署确定性的取舍，`docs/BUILD.md` 记录了安装后约 1.8 GB 的磁盘占用。两个 exe 的分工：`KianaLauncher` 是五页界面壳（含进程内引擎），面向"打开就能用"的操作方式；`KianaCrawler` 是纯命令行形态，面向脚本化与无人值守场景。两者共享同一个引擎包，行为差异只在控制面——命令行参数与 GUI 设置项最终翻译为同一份引擎配置。

### 2.2 进程模型：进程内引擎

引擎不是 GUI 的子进程。`EngineBridge` 在一个 daemon 线程里运行独立的 asyncio 事件循环，进程内直接调用引擎入口 `crawl()`；`print` 与 `logging` 两条输出被桥接为 Qt 信号回传界面。这个设计的收益有三：任务状态免序列化直读；调试时一个进程断点走全栈；打包产物不需要进程间协议。代价是必须严守一条纪律——**GUI 不允许直接触碰引擎对象**，只能经由桥的 stop/pause/resume 三个控制口与只读引用，否则 Qt 主线程与事件循环的线程边界会被打破。跨线程回主线程使用 `QApplication.postEvent` 而非信号直连，这是工程里用事故换来的规约。

退出码语义固定为四种：0 正常完成、1 主动停止、2 引擎崩溃、3 引擎加载失败。GUI 与 CI 都以这组语义为契约。

选择"进程内"而非"子进程"还有一个常被忽略的理由：**状态诊断的即时性**。子进程架构下，"任务现在卡在哪一步"要靠进程间协议回传或日志反推；进程内架构下，桥直接持有引擎的只读引用，暂停/恢复/停止是函数调用而不是消息往返。代价同样真实——引擎的崩溃从"子进程退出"变成"线程内异常"，必须被桥完整捕获并翻译为退出码 2，否则一次未捕获异常就带崩整个界面。这层翻译逻辑因此也进了测试。

### 2.3 一次抓取的完整路径

单页从入队到落盘共 17 步，可分三段：

- **建立段（1–3）**：创建任务目录（`cli_<sha8>/`，内含队列库、导出树、统计流 `stats.jsonl`、断点 `checkpoint.json` 与日志）；种子 URL 分流；入队。
- **执行段（4–12）**：取批（写租约）→ 取出口与并发名额 → 心跳续约 → 缓存命中判定 → 五级路由 → 解析炸弹闸 → 脱敏 → 去重 → 质量闸。
- **出口段（13–17）**：CAS 认领 → 持久化与导出 → 媒体入队 → 出链发现 → 统计。

这条路径上的每一步都有对应的故障预案：取批失败进死信、路由逐级升级、CAS 失守一字不写、看门狗到点击杀。第 4 节将看到"配置如何保证一个 GUI 开关不被静默丢失"，第 5 节将看到"这条路径如何被 675 个离线用例覆盖"。

### 2.4 运行期数据布局与密钥治理

运行期数据根由 `config.data_root()` 决定：默认在 `%LOCALAPPDATA%\KianaVnextPlus`；设置 `KIANA_PORTABLE=1` 时切换为 **exe 同级**的 `KianaData/`。后者的实现有一个容易踩错的陷阱：便携根**不得**取 `sys._MEIPASS`——在 PyInstaller onedir 布局下它指向 `_internal`，而卸载器会用 `RMDir /r` 清理安装目录，把数据根放进去意味着升级即丢数据。exe 同级目录不受卸载清理影响，这是实测后的选择。

凭据治理遵循"本机密钥不出本机"的原则：使用者提供的 cookies 经 `cookie-add` 子命令加密入库（Fernet，`cryptography` 提供），主密钥落盘为 `master.key` 并被 `.gitignore` 与门禁双重看守——门禁第 6、7 两项分别扫描密钥形态与凭据字面量，未跟踪产物也算脏。弹药库账号的健康状态可经 `cookie-list` 查看，程序侧没有任何内置凭据，示例中的占位符符合扫描规则。HTTP 缓存落盘的内容是脱敏后的（§3.5），因此缓存目录不构成二次泄漏面。

## 3 关键机制

### 3.1 可达性：五级回退调度

`engine_router.py` 按代价从低到高排布五级：协议通道（curl_cffi 的 TLS 指纹模拟）→ 隐身通道（源码级反检测）→ TLS 切换 → 真浏览器（patchright 主通道、playwright 兜底）→ 直连。前一级失败或撞上挑战时请求自动升级；低成本通道能拿到内容时，浏览器进程根本不会被拉起，这是并发下"浏览器风暴"不会发生的原因——渲染另有独立的预算上限。

两个设计细节值得一提。其一，**拦截与升级使用不同的信号**：被闸拦下的请求返回 400，而 403 被保留为"升级到浏览器层"的信号——混淆两者会让被拦截的 URL 跑进浏览器层白白付出渲染代价。其二，**隐身通道不做 JS 注入**：运行时属性伪装（`Object.defineProperty` 之类）会留下可检测痕迹，本工程走的是协议层修复与启动参数治理（patchright 提供 Runtime.Enable 泄漏修复），并显式区分"删 stealth"与"删 UX"两类改动。

回退调度的上游还有三个可选开关，各自对应一类合规或效率诉求：`--robots` 在链接入队前按域判定 robots.txt 合规；`--sitemap` 开启站点地图播种，把"给一个入口、抓全站结构"变成一次声明；cookie 弹药库（§2.4）为需要登录态的页面提供凭据，凭据不足时页面按诚实降级返回可读原因。这三个开关都不改变回退语义——它们决定"哪些 URL 值得进入回退调度"，回退调度决定"用什么代价取回它"。

### 3.2 一致性：租约与 CAS

前沿队列 `frontier.py` 是 SQLite 上的 8 张表，用 `PRAGMA user_version` 做到版本 5 的幂等迁移。并发正确性建立在两个原语上：

**租约**。取任务即写入 `leased_at` 与 `lease_expires`，60 秒心跳续约。心跳续的是 `lease_expires` 而不是 `leased_at`——改后者会破坏 CAS 闭环，这条边界写进了工程纪律文档。

**CAS**。结果落盘前必须赢一次比较交换；CAS 是三态的：赢（写入）、输（一字不写）、**数据库故障（None，必须抛出重试）**——把 `None` 当作"输了"处理，会让锁库故障被静默吞成"被别人抢先"。失败路径同样有守卫：`mark_failed` 的 UPDATE 必须带 `AND status != 'done'`，否则看门狗会把已经完成落库的页面打回重试，造成整页重爬与重复导出——这是本工程真实发生过的缺陷，现为回归用例。

死信队列是这套协议的最后一级：重试次数耗尽或限流计数越限的页面进入死信而非无限滞留，任务因此**总能结束**——结束不等于全部成功，而是每种结局都有归属。死信页携带失败原因分类，`retry-dead` 子命令可以把它们成批重新入队（例如换一批出口 IP 之后），`errors` 子命令则聚合展示失败分布。一个长跑任务的健康度因此可以量化：完成、死信、跳过各自多少，而不是一个含混的"跑完了"。

竞态防控有一条统一规约：**跨 `await` 的读-改-写就是真竞态，正确写法是"同步块内先占位再 await"**。robots 门闸与渲染预算都按此实现。

数据库并发还有一个常被误判的边界：`database is locked` 与"租约易主"是**两类事件**。前者是 SQLite 写锁冲突，每条连接因此设置了 `busy_timeout`，锁库时应等待或抛出重试；后者是另一个 worker 已合法接管任务。CAS 的三态设计（§3.2）正是为了让这两类事件不可能被同一个分支吞掉——`None`（库故障）必须走异常路径重试，而不是被当作"输了"静默放弃。

### 3.3 流控：两级令牌桶与可终止的重试

限速是全局与按域的两级令牌桶。它最重要的设计不是桶本身，而是**重试语义的切分**：被限流（throttled）不消耗重试预算，走独立的 `throttle_count`，连续多次后转死信；真正的传输失败才递增 `retry_count`。没有这个切分，限流期间任务会永驻重试队列，主循环的退出条件永远无法成立——任务"跑不完"而不是"跑得慢"。`Retry-After` 头遵守但封顶 300 秒，防止单个站点用一个头把整批任务挂起数小时。并发参数：全局 20–50 路协程，每域并发 20；三级仲裁取最小值，且控制器停止/恢复时必须归还诉求并重算，否则一次风控降级留下的低值会永久钳死并发。

与限速配套的还有一层**传输语义的切分**：传输异常必须抛出，而"被闸拦下/协议非法"才返回空值。两者混同的后果是把一次网络抖动当成永久失败（丢失可重试的机会），或把一次确定性的拦截当成可重试的故障（白白重试到死信）。调用方据此靠 `except` 决定重试，靠返回值决定放弃——语义边界写在 `safe_get` 的契约注释里。

### 3.4 出口安全：逐跳 SSRF 防护

这是本工程代价最高的一课。**只在入口校验 URL 是不够的**：一个外部图片地址可以返回 302 指向内网，底层 HTTP 库会自动跟随——本机用两个回环服务实测复现了"内网响应被当作图片正常落盘"。`url_utils.py` 由此成为全仓被引用最多的模块，所有出网取流必须经过它。

之所以收口到**一个共享原语**而不是各通道自建校验，是因为安全检查的失效模式恰恰是"漏了一处"：引擎里有主抓取、媒体下载、m3u8 分片、链接发现多条出网路径，任何一条自建校验都会在未来某次改动里被遗忘。共享原语使"新增出网路径默认安全"，绕过原语反而需要刻意写出一行非常规代码——这在评审里是一眼可见的。具体机制：

- **入口校验 + 关闭自动重定向 + 逐跳复检**。curl_cffi 默认跟随 30 跳重定向且其响应对象没有 `.url` 属性，复检落点只能靠手动逐跳实现。
- **主机名规范化**：IPv6 zone id 与 FQDN 尾点都曾被用来绕过黑名单，先归一再判定。
- **25 种私网形态**，覆盖标准库遗漏的段落，含十进制、十六进制、八进制 IP 变体。
- **DNS 判定 90 秒过期**：阻断"首次解析到公网、稍后改指内网"的 rebinding 手法。
- **重定向上限 10 跳**。

一个反直觉的例外被显式记录：`llm_client` 不套闸——那里是使用者自填的推理端点（如本机 Ollama），套闸会把 `http://localhost:11434` 这类本地服务拦死。安全机制必须允许有理由的例外，但理由要写在注释里。

### 3.5 数据卫生：三层脱敏与显式边界

脱敏覆盖三个泄漏面：**日志**（过滤器挂在 handler 上——Python logging 只调用祖先的 handler、不调用祖先 logger 的 filter，挂在 root logger 上等于没有；新建 handler 由 `config.py` 包装自动获得脱敏）、**旁路**（print 桥、GUI 日志、异常回显各自过一遍）、**产物**（导出副本经 `sanitize_record` 逐记录脱敏，递归 6 层）。共 19 类敏感 URL 参数（token/key/sign/session/csrf 等）与手机号、邮箱、IP 模式。HTTP 缓存落盘的内容也是脱敏后的。

**边界同样被显式化**：任务队列里的 URL 不脱敏。它们是"稍后还要再请求一次"的钥匙，抹掉签名参数会让续爬直接 403。这条"哪里绝不脱敏"的推理写进了代码注释与工程纪律，防止后来者出于好意"顺手补闸"把功能改坏。

导出格式侧同样有字节级的边界案例：CSV 的 UTF-8 BOM **只允许在新文件首次写入时出现一次**，追加模式不得使用 `utf-8-sig`——否则每次追加都会再写一个 BOM 到文件中部，从第二批数据起整列被污染。这曾是真实缺陷，现为回归用例。

脱敏的参数识别走**显式清单而非泛匹配**：`_URL_SECRET_RE` 逐条列出 19 类敏感参数名（token/key/sign/session/csrf 等）。泛匹配（如"参数名含 key 就删"）的误杀率不可控——会把业务参数一并抹掉；显式清单的代价是新型参数需要补录，但每一条都在评审之下。这是"宁可漏一点、不可错一片"的取舍，与 §3.4 私网形态用穷举表而非正则推断是同一个方法论。

### 3.6 媒体面：直链解析与无损下载

四个平台解析器（抖音、小红书、快手、网易云）采用表驱动分派：`_PLATFORM_RESOLVERS` 一行一个平台。解析策略是**先读页面已有的数据**（`window.__INITIAL_STATE__`、JSON-LD），而非凭空构造请求参数；产物统一收敛到 `MediaItem`（`source / media_id / kind / streams / images / method` 等字段），上层只认一个 schema。签名算法（如抖音 a_bogus 的 SM3 链路，`gmssl` 提供）按公开协议事实实现，配逐字节固定向量做回归——协议事实层不依赖"网站现在还这么返回"的假设，向量回归能把实现漂移在提交前拦住。

两条硬约束挂在接入协议上：resolver 是纯同步实现，必须经 `asyncio.to_thread` 调用，否则冻结整个事件循环（抖音曾因此冻结 30–80 秒）；解析出的直链来自远端页面状态，必须过 `is_private_url` 复检——这正是 §3.4 的闸在媒体通道上的延伸。

下载器保证**无损与原子**：先探测总大小与 Range 支持，流式写 `.part`，按字节偏移续传，按字节数自校验，最后原子改名——下游永远看不到半截文件。m3u8 分片含 AES-128 解密（pycryptodome）；ffmpeg 只用于合并分片，**不做任何重编码**；服务端不支持 Range 时弃旧 `.part` 重下，绝不拼接出坏文件。视频是字节搬运；音频仅在显式开启音频通道时转 MP3。B 站弹幕的可选 ASS 转换走独立组件（未安装时自动跳过、不阻塞任务），体现同一条原则：**可选能力缺席不构成故障**。

### 3.7 挂起治理：看门狗与阻塞卸载

单页看门狗默认 300 秒（正常页 < 60 秒，5 倍余量），可配置、可用 `--page-timeout 0` 显式关闭——v2.19.8 修复了该参数"传了也不生效"的透传缺陷。超时页被击杀并标记重试，不连累同批其他页。与看门狗配套的是一条全仓纪律：**阻塞调用一律 `asyncio.to_thread`**——SimHash 指纹、全文脱敏、文件 IO、同步 resolver 全部在内；事件循环里不允许出现会阻塞的调用。

Windows 平台另有两类平台特有的挂起与静默失败，各有固定解法并已写进陷阱表。其一是**子进程编码**：yt-dlp 调 ffmpeg 时，子进程输出默认按系统 GBK 解码，中文文件名轻则乱码、重则静默失败——解法是文件名改为哈希、`locale` 强制 C.UTF-8。其二是**中文路径读图**：`cv2.imread` 在 Windows 上遇到非 ASCII 路径会静默返回 `None`（不抛异常），解法是 `np.fromfile` + `cv2.imdecode`。两者的共同点是失败模式安静——不写进陷阱表，下一个维护者会以为功能是坏的而代码是好的。

### 3.8 可观测性与可恢复性

长跑任务的生命线是"随时知道它在干什么、断了能接上"。可观测性方面：统计经 `stats.jsonl` 以追加流落盘，GUI 统计卡与 CLI `status` 子命令消费同一份契约；失败与错误档案可经 `errors` 子命令聚合分析，把"这次跑了多少、坏在哪类站点"变成可回答的问题。可恢复性方面：任务目录里的 `checkpoint.json` 记录断点，进程重启后从断点续跑；失败页进入死信队列后可用 `retry-dead` 子命令重新入队，而不是从头再来；队列本身持久于 SQLite，导出树按域名分目录落盘（JSONL / CSV），媒体按类型归档——任务目录是自包含的，可以整个拷走分析。

这套设计的取舍是"文件优先"：不引入额外的观测服务或数据库依赖，一切状态都是磁盘上可直接查看的文件。对单机工具，一个能用文本编辑器打开的 `stats.jsonl` 比一个需要先起服务才能看的面板更可靠；诊断也因此在离线的机器上同样可行。

## 4 扩展模型

### 4.1 声明式站点规则

加一个站点不改代码：写一条 `rules/sites/<域名>.yaml`，用 `rule-new` 生成骨架、`rule-validate` 校验、`rule-test` 对本地样例试跑——三个子命令构成规则的"编写-校验-回归"闭环，全程离线。12 条既有规则每条强制配套一份从真实页面抓取的 HTML 样本，发版门禁会核对样本清单（当前 10 个站点域的样本齐备）——这意味着规则层的回归不依赖任何实时站点，站点改版也不会让测试套件连夜变红，而是由实站回归线（门禁第 9 项）单独暴露。规则约定了 `exclude` 键，把导航、广告、播放页之类的 URL 排除在正文抓取之外，避免与视频、音乐通道互相抢任务。

### 4.2 平台解析器接入协议

新平台 = 新建 `<site>_resolver.py`（返回同构 `{ok, ...}` 字典并经 `media_schema` 收口）+ 在分派表加一行 + 视需要加入 59 项（去重后）的国内直连名单 `exit_manager._DOMESTIC_DOMAINS`——名单的存在是因为海外代理 IP 访问国内站点会触发风控，B 站的极验挑战是实测案例。名单当前 63 条原始条目、去重 59 个。

"同构 `{ok, ...}` 字典"是接入协议的关键约束：resolver 的失败也是数据（`ok: false` 加原因），不是异常——下载链因此可以把"解析失败"当作"该平台没帮上忙"，保持原 URL 走通用通道继续，而不是让一个平台的故障打断整批下载。直链截取统一走 schema（优先 `media.streams[0].url`，退回平台历史键），调用方不需要知道四个平台各自的响应结构。这套约定让"新增平台"的代码量稳定在一个文件加一行，并且两个硬约束（to_thread、私网复检）写进了接入文档——扩展点的安全性不依赖扩展者的记忆力。

### 4.3 配置一致性：六点接线

GUI 的一个设置项要经过六个环节才能生效：控件创建 → 接线 → 启动配置 → `EngineBridge` 翻译表 → `crawl()` 的显式键表 → `DEFAULT_GLOBAL` 默认值。**漏掉任何一环 = "能填不生效"**，且不报错。本工程把六点清单写进工程纪律并要求新增设置项逐点核对——这来自一次真实事故：`--page-timeout` 曾在 argparse、GUI、键表三处都通不过，直到 v2.19.8 才以 `page_timeout_override()` 纯函数收口。

配置系统有一个贯穿性的原则：**`DEFAULT_GLOBAL` 是引擎配置的唯一默认源**。界面层（`launcher_config.json`）与引擎层各持一份配置，桥的翻译表只做"界面键 → 引擎键"的搬运，默认值不许在两处各写一份——否则改一处漏一处，同一参数在不同入口下行为不同。`page_timeout_override()` 之所以做成纯函数，正是为了把"显式指定才覆盖"的判定收敛到一个可单测的位置：CLI 不传时返回空、引擎回落默认 300 秒；显式传 0 时无条件透传，看门狗真正关闭。"未指定"与"显式为零"从此是两个可区分的状态——这是配置系统里最容易被忽略、也最容易在事故复盘时被误判的一类缺陷。

### 4.4 界面工程：五页控制台与壁纸渲染管线

桌面界面共五页（首页 / 日志 / 数据 / 任务 / 设置），构建在 qfluentwidgets 的 FluentWindow 之上。界面工程里有两条用事故换来的纪律。其一是**页面构建只在 `__init__` 执行一次**：历史上一次缩进事故让桥接与页面构建在每次窗口 Show/Resize 时重跑，单次重建约 1,910 个控件、卡顿 7.6 秒——回归后重建成本为零。其二是**统计卡必须显式注册**：早期实现用 `findChildren` 按对象名扫描统计标签，控件树一变就"接好了但不更新"且无任何报错；现改为显式注册表 `_stat_labels`，漏注册会在评审时肉眼可见。引擎侧的统计经 `stats.jsonl` 作为消费契约喂给界面，两侧只认文件不认对象。

壁纸渲染管线是界面里最重的一块图像处理：支持单张与文件夹轮换、封面裁切（九宫格焦点控制偏移）、0–30 档高斯模糊、基于亮度分析的自动蒙层（亮图多蒙、暗图少蒙）、两层 Label 交叉淡入淡出，以及从壁纸提取强调色（HSV 过滤后取直方图众数，可锁定为手选色，与取色模式互斥）。管线的全部参数变更走 200 毫秒防抖并按 `(路径, 尺寸, 模糊, 蒙层, 焦点)` 做结果缓存，重采样不重复计算；重活全部在 `to_thread` 中执行，Qt 图形对象只在主线程构造。右下角的电子签名水印默认**为空**——程序不内置任何默认文案，是否落款、落什么款完全由使用者自填。

## 5 质量保障体系

### 5.1 离线测试线

675 个用例（674 通过 / 1 跳过）全部离线——测试套件不发起任何真实网络请求。离线不是妥协而是设计：站点规则以真实页面 HTML 样本为fixture，签名算法以固定向量为断言，并发一致性以内存库为靶子。全量测试的通过判据被门禁固定为"≥400 passed 且 0 failed"。

测试套件的组织方式反映了工程的演进史：用例文件按版本批次命名（`test_v218_*`、`test_v219_*`、`test_v2198_*`），每个批次对应一次版本交付引入的机制与修复的缺陷。这样组织的收益是**可追溯**——看到一条失败用例的文件名，就知道它守护的是哪一批机制；也便于在版本重构时判断哪些用例承载的是不变式、哪些只是当时的实现细节。唯一被跳过的用例按 `skipUnless` 条件挂起（依赖特定环境），跳过机制本身也被门禁的计数口径覆盖。

### 5.2 十项发版门禁

`python tools/release_check.py` 一次跑完十项，任一失败即禁止发版：

| # | 检查 | 说明 |
|---|---|---|
| 1 | 版本一致性 | `VERSION.json` / `pyproject.toml` / `__init__.py` / NSIS 四处同步 |
| 2 | Git 卫生 | 工作区干净（未跟踪文件也算脏） |
| 3 | 全量测试 | ≥400 passed 且 0 failed |
| 4 | 静态检查 | ruff 82 / mypy 103，基线锁死（≤84 / ≤104），只许降不许升 |
| 5 | 依赖审计 | pip-audit 对钉死版本比对漏洞库（本版实测：无已知漏洞） |
| 6 | 密钥扫描 | 包内无私钥/真实 API key 形态 |
| 7 | 凭据卫生 | 仓库零 cookies/密钥字面量 |
| 8 | 规则资产 | 12 条规则全部加载；真实样本 10/10 齐备 |
| 9 | 实站回归 | 多线验证（含离线规则线） |
| 10 | 构建面 | 入口可编译、spec 存在；PO Token 缺件会在打包期硬中止 |

十项门禁的设计哲学可以概括为一句话：**把"发布前应该检查的事"变成"发布前必须通过的事"**。它的每一项都对应一种单人项目特有的失效方式——版本号改了三处漏一处、工作区留着未跟踪的调试产物、静态告警悄悄回升、密钥随手写进示例、规则加了样本没加。门禁不提供"跳过但警告"的中间态：FAIL 就退出码 1，SKIP 必须显式声明理由（如 `--skip-network`）。静态基线锁死为"只许降不许升"是其中最反直觉也最有效的一项：它不要求代码完美，只要求**不要比昨天更糟**——对单人维护的仓库，阻止回退比追求完美现实得多。

### 5.3 依赖治理与供应链

25 条运行时依赖 + 6 条开发依赖全部 `==` 钉死，每条是本机实测过的组合（curl_cffi 0.16.0、yt-dlp 2026.7.4、patchright 1.61.2、PySide6 6.11.1、PySide6-Fluent-Widgets 1.11.3、cryptography 50.0.0 等）；升包必须重跑门禁并按需调整锁死的静态基线。许可逐项盘点：两个 GPLv3 组件（GUI 框架与 PO Token 插件）决定了工程整体按 GPL-3.0 授权（§8）；随包字体与插画的许可与来源单独成文声明。CI 在 GitHub Actions 上复跑版本一致性、静态检查、全量测试与覆盖率报告。

### 5.4 构建与发布工程

发布链路由 `一键构建.bat` 串起七步：依赖核对 → 双 PyInstaller 构建 → 产物完整性检查 → NSIS 打包 → GUI/CLI 冒烟 → 发版门禁 → 产物归档。两个 spec 分别对应控制台（`KianaCrawler.spec`）与 GUI（`KianaLauncher.spec`）两个 exe，前者是引擎的纯命令行形态，后者是五页界面壳——两者共享同一个引擎包，spec 只决定入口与资源收集面。构建侧的硬约束同样来自事故：

- **PO Token 组件缺件会硬中止构建**——spec 在收集阶段检查 vendor 目录（Node 服务与 deno 运行时），缺件直接 `raise SystemExit`；逃生舱 `KIANA_SKIP_POT=1` 只允许自用测试构建。这是用"曾经静默打包成功、装出去才发现组件缺失"的教训换来的。
- **打包后强制产物完整性检查**：`_internal` 下必须找到 `deno.exe`、`build/main.js`、`chrome.exe`，任一为空即判构建失败。
- **qfluentwidgets 的资源文件必须随包收集**（`collect_data_files`），漏掉的症状是打包后界面白屏——它带 SVG/QSS/字体资源，纯代码收集看不见它们。
- **NSIS 多语言安装器**的语言文件是生成物（由 `tools/gen_nsis_langs.py` 生成，禁止手改）；卸载器是**三分支条件逻辑**（注册表安装且可恢复 → 恢复原安装；注册表安装且不可恢复 → 彻底清理；无注册表 → 只删自身），其中快捷方式恢复分支曾因 NSIS `CreateShortCut` 取当前 `$OUTDIR` 作起始位置而把恢复出来的快捷方式指进临时目录，v2.19.8 以 `SetOutPath` 显式重定根修复。
- **在 Git Bash 里调 makensis 必须经 python subprocess**：MSYS 会把 `/S` 一类的开关改写成 `S:/` 路径——一个不写下来就必然重踩的坑。
- 安装/卸载矩阵测试覆盖 8 种语言界面，实测安装、卸载、残留核对三段；测试副本**绝不**用正式安装的 `Uninstall.exe` 卸载，静默探针结束后必须 `TerminateProcess`（发 `WM_CLOSE` 会触发连环弹窗）。

### 5.5 回归用例举隅：从事故到用例

本工程的测试不是按覆盖率凑数，而是**每条真实事故固定为一条回归用例**。几个代表性样本：

| 事故 | 回归断言 |
|---|---|
| 风控降级后全局并发被永久钳死（GREEN 恢复不归还诉求） | 恢复后 min-wins 诉求必须归还 |
| 看门狗把已完成落库的页打回重试（整页重爬 + 重复导出） | `mark_failed` 带 `status != 'done'` 守卫 |
| `database is locked` 被当作租约易主静默吞掉 | CAS 三态：`None` 必须抛出 |
| 被限流的任务永驻重试队列，主循环永不退出 | throttled 不递增 `retry_count`，独立死信计数 |
| CSV 追加写入 BOM 污染第二批数据 | BOM 仅新文件首写一次 |
| 裸 `session.get` 跟随 302 把内网响应存成图片 | 25 条 SSRF 对抗 URL（十进制/十六进制等变形）全部拦截 |
| 抖音 resolver 直链漏过私网复检 | 媒体通道直链必经 `is_private_url` |
| `--page-timeout 0` 传不进引擎 | 显式值（含 0）无条件透传，`0` 可关看门狗 |

这张表是第 3 节各机制存在的原因——机制不是设计出来的，是事故逼出来的，然后用例钉住。新贡献者读测试时建议按这张表对照源码：每条断言背后都有一个"如果没有它会再次发生"的故事。

## 7 已知边界与未决项

以下各项按原样陈述，不做修饰——这份清单本身就是工程姿态的一部分：

1. **部分平台解析器仅有离线测试证据**，没有对实时服务的端到端验证；缺登录态时按"诚实降级"处理——返回可读原因而非强行绕路。缓解：实站回归线（门禁第 9 项）覆盖主要平台，离线与在线两层证据各自记录。
2. **少数实站解析当前失败**，原因尚未定位；在定位前保持为未决项，不断言是平台侧变更。缓解：失败档案可经 `errors` 子命令聚合，定位有数据可依。
3. **安装包 542 MB** 偏大——这是"运行期零下载"的代价，见 §2.1 的取舍说明。缓解：安装器一次交付，卸载器三分支清理彻底（§5.4）。
4. **覆盖率只报告不设阈值**（历史基线约 52%）；LLM 增强默认关闭。不做阈值强制的理由：这批离线用例的主要来源是事故回归而非行覆盖，行覆盖率在当前阶段不是有效质量信号。
5. **单人维护**是工程事实：十项门禁与锁死的静态基线是对这个现实的工程回应，但不改变总线风险。缓解：全部机制与陷阱已成文（`CLAUDE.md`、`docs/DEVLOG.md`），交接成本低。

## 9 结论

kiana-crawler 的工程价值不在于功能清单的长度，而在于**每个声称都有出处、每个边界都被写出**：五级回退对应五种真实的拦截手段，租约与 CAS 对应两类真实发生过的并发事故，逐跳 SSRF 闸对应一次本机复现的攻击，十项门禁对应单人维护的全部失效模式。对一位在 Windows 上需要一台"装完即用、行为可预期、产物干净"的采集机的使用者，它提供的是一个可以被逐条验证的答案；对其余场景，第 1.3 节与第 7 节的边界清单给出了诚实的"不"。

如果要再压缩成一段话：这个工程把"个人项目"最常见的三种死法——静默并发故障、静默安全漏洞、静默的"能填不生效"——各自对应的机制（CAS 三态、逐跳闸、六点接线）做成了显式契约，再用一条把"任何一项失败就禁止发版"的门禁把契约钉住。它的可信度不来自承诺，而来自**打开仓库五分钟内就能复核本文任何一句**。对工程实践有兴趣的读者，`tools/release_check.py` 与 `tests/` 是比本文更好的起点：机制在代码里，事故在用例里。
