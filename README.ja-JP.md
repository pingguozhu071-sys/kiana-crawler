## これは何か

Windows 向けの**単機収集エンジン**です。自己完結した asyncio クローラコアを中核とし、PySide6 のデスクトップインターフェースを操作面として備えています。

設計は「対応サイト数」ではなく、次の 4 つの問題を軸に構成しています：

| | 問題 | アプローチ |
|---|---|---|
| **取得** | サイトは TLS フィンガープリント、JS チャレンジ、挙動検知でコンテンツを制限する | 五段フォールバック：プロトコル → ステルス → TLS 切替 → 実ブラウザ → 直結 |
| **解析** | マークアップがサイトごとに異なる | 汎用本文抽出 + 宣言的サイトルール + 埋め込み JSON 解析 |
| **データ品質** | 重複、空のページ、出力に混入する個人情報 | 内容フィンガープリントによる重複排除 + 品質ゲート + 三段のマスキング |
| **安定性** | 数十の同時リクエスト、数時間の連続実行、ハングするページ | リース + CAS による一貫性 + ページ単位のウォッチドッグ + トークンバケットによるレート制限 + レジューム可能なダウンロード |

## 技術ハイライト

各ハイライトは同じ四部構成です：**問題 → 実装 → 主要な数値 → 該当モジュール**。

### ① 五段フォールバック：コンテンツ到達性

> **問題**：サイトによってコンテンツの出し方が異なります。そのまま配信するサイトもあれば、TLS ハンドシェイクを指紋で判定するサイトもあり、実際の JS 実行後にしか描画しないサイトもあります。単一の戦略ではこの 3 つすべてをカバーできません。

- **実装**：コストの低い順に五段 —— プロトコル（TLS 偽装）→ ステルス → TLS 切替 → 実ブラウザ → 直結。失敗またはチャレンジ検知でリクエストを次の段へ昇格します。安価な経路で成功すれば、ブラウザは起動しません。
- **主要な数値**：5 段 · 同時実行 20–50 コルーチン · ブラウザ描画には専用の予算上限（ブラウザの乱発を防ぐ）
- **該当モジュール**：`engine_router.py`（スケジューリング）· `protocol_engine.py` · `solver_engine.py`

### ② プラットフォームリゾルバ：メディア URL の直接抽出

> **問題**：メディアサイトは再生可能な URL を埋め込み JSON の中に保持しており、署名付きで有効期限もあります。ページ URL を汎用ダウンローダーに渡す方法では、利用可能な最高画質を取り逃すことが少なくありません。

- **実装**：要求パラメータを組み立てる前に、**ページがすでに保持している内容**（`window.__INITIAL_STATE__`、JSON-LD）を読み取ります。4 つのプラットフォームリゾルバはすべて単一のスキーマ（`MediaItem`：source / media_id / kind / streams / images / method）に収束するため、呼び出し側は 1 つのフィールドを参照するだけで済みます。ページ状態から抽出した URL は使用前に SSRF ゲートで再検査します。
- **主要な数値**：4 リゾルバ（Douyin / Xiaohongshu / Kuaishou / NetEase Cloud）· 単一の統一スキーマ · 抽出した URL はすべて再検査
- **該当モジュール**：`media_schema.py` · `*_resolver.py` · `universal_downloader.py`（テーブル駆動の振り分け）

### ③ リース + CAS：正確に 1 回の処理

> **問題**：並行処理で典型的な 2 つの故障 —— 2 つのコルーチンが同じページを処理してしまう（出力の重複）、または他のワーカーがすでに作業を確保した後に結果を書き込んでしまう（状態の破壊）。

- **実装**：作業を確保する際にリース（`leased_at` / `lease_expires`）を書き込み、60 秒のハートビートで更新します。**何かを永続化する前に、ワーカーは CAS（compare-and-swap）を勝ち取る必要があります**。負けた場合は何も書き込みません。ウォッチドッグと失敗経路には「完了済みを上書きしない」ガードがあります。
- **主要な数値**：ハートビート 60 秒 · ページ単位のウォッチドッグ 300 秒（設定可能、無効化も可能）· CAS は三状態（勝ち / 負け / DB 障害）
- **該当モジュール**：`frontier.py` · `page_processor.py`

### ④ ウォッチドッグと二段レート制限：実行の安定性

> **問題**：ページが 1 つハングするだけでバッチ全体が停止します。また、雑なレート制限は終わらないリトライの連鎖になります。

- **実装**：タイムアウトを超えたページは打ち切り、バッチ全体を巻き込まずに再試行対象としてマークします。レート制限は**二段のトークンバケット**（全体 + ドメイン別）です。スロットルされても**再試行の回数は消費しません** —— 別カウンタと独自のデッドレター閾値で扱うため、メインループの終了条件が実際に成立します。
- **主要な数値**：ウォッチドッグ **300 秒**（通常ページは 60 秒未満、余裕は 5 倍）· ドメイン別同時実行 **20** · `Retry-After` の上限は **300 秒**
- **該当モジュール**：`crawler.py` · `rate_limiter.py` · `concurrency.py`

### ⑤ 再エンコードなしのレジュームダウンロード

> **問題**：大きなダウンロードが中断した場合、最初からやり直すべきではありません。また、再エンコードは原本の品質を損ないます。

- **実装**：まず総サイズと Range 対応を確認 → `.part` ファイルへストリーム書き込み → 正確なバイト位置から再開 → バイト数を検証 → **原子的リネーム**（下流が部分的なファイルを参照することはありません）。動画は再エンコードせずバイト単位で転送し、音声は音声チャンネルが有効な場合にのみ MP3 へ変換します。サーバーが Range に対応していない場合、古い `.part` は連結せず破棄します（壊れたファイルを作らないため）。
- **主要な数値**：バイト数の検証 + 原子的な配置 · AES-128 復号を伴う m3u8 フラグメント対応 · ffmpeg は**結合**にのみ使用し、再エンコードには使用しない
- **該当モジュール**：`universal_downloader.py` · `m3u8_downloader.py` · `media_downloader.py`

### ⑥ ホップ単位の SSRF ゲート

> **問題**：**入口 URL の検証だけでは不十分です。** 外部の画像 URL が 302 で内部アドレスを指せば、基盤の HTTP ライブラリはそのまま追従し、**内部のレスポンスが通常の画像としてディスクに書き込まれます。** ローカルの 2 つのループバックサービスで再現済みです。

- **実装**：すべての外向き取得は 1 つの共有プリミティブを通ります —— 入口で検証し、自動リダイレクトを無効化し、**ホップごとに追跡して再検証**します。まずホスト名を正規化します（IPv6 ゾーン ID と末尾ドット付き FQDN はいずれもブロックリストをすり抜ける経路でした）。プライベートネットワークの判定は標準ライブラリが対象外とする範囲もカバーします。DNS の判定には 90 秒の有効期限を付け、「先に公開アドレスへ解決させ、後で内部へ向け直す」リバインディングを封じます。
- **主要な数値**：リダイレクト上限 **10 ホップ** · DNS 判定の TTL **90 秒** · 25 のプライベートアドレス形式をカバー · 10 進 / 16 進 / 8 進の IP 表記にも対応
- **該当モジュール**：`url_utils.py`（リポジトリ内で最も被参照数の多いモジュール）· すべての取得・発見経路

### ⑦ 三段のマスキングと明示された境界

> **問題**：URL 内の電話番号、メールアドレス、トークンが結果に混入することは現実的なリスクです。**マスキングには境界もあります** —— 適用箇所を誤ると機能が根本から壊れます。

- **実装**：三段構成です —— ログ（フィルタは **handler** に付与します。root logger に付与しても何も起きません）、サイドチャネル（print ブリッジ、GUI ログ、例外の出力）、成果物（エクスポートされるコピーはレコード全体に対して処理します）。
  **除外は明示的です**：タスクキュー内の URL は「後続のリクエスト」のためのキーです。署名パラメータをマスキングすると再クロールが 403 で失敗します。この理由はコードのコメントに記載してあり、後から「親切心で」壊されないようにしています。
- **主要な数値**：**19** 種の機微な URL パラメータ · 電話 / メール / IP · レコード単位の再帰は深さ 6 まで
- **該当モジュール**：`sanitizer.py` · `config.py`（配線）· `page_processor.py`（エクスポートコピー）

### ⑧ 十項目のリリースゲート

> **問題**：単独で保守するプロジェクトでは、壊れたリリースの原因は検証されなかった前提であることがほとんどです。

- **実装**：コマンド 1 つで十項目を検査し、**1 つでも失敗すればリリースをブロックします**：4 つのファイルの版一致 · git 作業ツリーがクリーン · 全テスト · 静的解析（基準は固定、下げる方向のみ可）· 依存関係の監査 · シークレットスキャン · 資格情報の衛生 · ルールとアセットの完全性 · 実サイト多系統の回帰 · ビルド面。
- **主要な数値**：**10 項目** · **675 件のオフラインテスト** · 静的解析の基準は現在の実測値に固定（下げる方向のみ可）
- **該当モジュール**：`tools/release_check.py` · `.github/workflows/ci.yml` · `tests/`

## アーキテクチャ

```
launcher_v9.py          GUI 入口（五ページ：ホーム / ログ / データ / タスク / 設定）
  └ launcher_v8.py      有効なシンボルは 4 つのみ（エンジンブリッジ、ログブリッジ、設定パス、シークレット）
run_crawler.py          コマンドライン入口 —— GUI のプロセス内エンジンでもある
  └ crawler.py          エンジン組み立て（7 つの _init_* が配線表、run() がメインループ）
      ├ engine_router.py      五段フォールバックのスケジューリング
      ├ page_processor.py     単一ページのパイプライン
      ├ frontier.py           SQLite キュー（リース / CAS / マイグレーション）
      └ url_utils.py          セキュリティプリミティブ（被参照数が最大）
```

**1 ページの処理の流れ**（17 ステップ）：

```
タスクディレクトリ作成 → 種の振り分け → 投入 → バッチ取得（リース）→ 出口と枠を確保 → ハートビート
  → キャッシュ命中？ → 五段ルーティング → 解析爆弾ガード → マスキング → 重複排除 → 品質ゲート
  → CAS 確保 → 保存/書き出し → メディア投入 → リンク発見 → 統計
```

**実行形態**：単一プロセス、asyncio コルーチン。スレッドはブロッキング呼び出しを逃がすためにのみ存在し、**マルチプロセスは使用しません**。エンジンは**サブプロセスではありません**。GUI は専用のイベントループを持つデーモンスレッド内でエンジンを実行し、`print` と `logging` を UI へブリッジします。

## クイックスタート

**必要環境**：Windows 10/11 x64 · Python ≥ 3.11

```bash
# 1. 依存関係をインストール（実行時 + 開発、すべて版固定）
pip install -r kiana_vnext_plus/requirements.txt
pip install -r requirements-dev.txt

# 2. デスクトップ UI を起動
python launcher_v9.py

# 3. またはコマンドラインから実行
python run_crawler.py "https://example.com" -d 0 -m 1 -o ./out
python run_crawler.py -f urls.txt -d 3 -m 500 -o ./out

# 4. テストスイートを実行（オフライン）
python -m pytest tests -q

# 5. リリースゲートを実行（10 項目）
python tools/release_check.py
```

主なオプション：`-d` 深さ（`0` = シードのみ）· `-m` ページ上限 · `-o` 出力ディレクトリ · `--strategy bfs|dfs|bff` · `--page-timeout` ページ単位のタイムアウト（`0` = 無効）· `--robots` で robots.txt 準拠を有効化。

**サイトの追加**（コード不要）：`rules/sites/<domain>.yaml` を作成 → `python -m kiana_vnext_plus.cli rule-validate rules/sites/<domain>.yaml` で検証 → `rule-test <file> --url <url>` でドライラン。

## 境界と正直な注記

既知の制限は、未解決のものを含めて明示します。

**実際の境界**

- **公開ページの対ボット対策には対応します**：TLS 偽装、実ブラウザへのフォールバック、チャレンジの解決、任意の CAPTCHA サービスキー。これは中核機能であり、上のハイライト①に記載しています（省略していません）。
- **アカウント権限には踏み込みません**：ログインウォール、ペイウォール、アカウント単位のコンテンツには、*利用者自身が用意した* Cookie がある場合にのみ到達します。それで不足する場合は、強行せずに判読可能なエラーを返します。
- **フレームワークでもサービスでもマルチユーザー向けでもありません。** 1 人が 1 台のマシンで使うことを想定した設計です。
- **個人データの収集は行いません。** 連絡先、メールアドレス、IP は書き込み前にマスキングされます。

**現時点で対応していないこと（明示）**

- 一部のプラットフォームリゾルバは**オフラインテストでのみ検証済み**であり、実サービスに対するエンドツーエンドの証拠はありません。ログインセッションがない場合は正直に機能を低下させ、強引な回避策ではなく判読可能な理由を返します。
- 一部の実サイト向けリゾルバは現在失敗します。原因は特定できていないため、プラットフォーム側の変更と断定せず未解決項目としています。
- インストーラは大容量（約 542 MB）です —— ブラウザのバイナリを同梱し、実行時のダウンロードなしで「インストールしてすぐ実行」を実現するためです。
- カバレッジは報告しますが、しきい値としては強制していません。LLM を利用する機能は既定で無効です。

**一行でいうと**：公開されているコンテンツを確実に収集します。アカウント権限や支払いの背後にあるコンテンツに到達するためのツールではありません。
